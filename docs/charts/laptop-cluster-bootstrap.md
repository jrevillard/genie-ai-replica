# Bootstrapping the laptop minikube cluster

The GENIE chart is developed against a local minikube cluster. This
document is the reproducible procedure to build that cluster from
nothing: which pieces live only inside a cluster, what order they have
to come up in, and how the two secret mechanisms (SealedSecret and SOPS)
differ.

Everything here is scripted in
[`scripts/laptop-cluster-bootstrap.sh`](../../scripts/laptop-cluster-bootstrap.sh).

## Why the cluster is rebuilt with Calico

minikube's default CNI (kubenet) has **no policy engine**. The
NetworkPolicy objects the chart renders are accepted and stored by the
API server, and nothing ever applies them. Consequences:

- every pod-to-pod connection succeeds, whether or not the chart's
  policies allow it;
- a laptop cluster stays green while carrying a broken egress graph;
- the defect only shows up in production, on a cluster running Calico,
  Cilium or kube-router — as a connection that times out with no error
  anywhere.

`minikube start --cni=calico` makes the laptop behave like the cluster
the chart is written for. The flag is stored in the profile, so later
`minikube start` calls on that profile keep it.

The static cross-check (`scripts/networkpolicy-crosscheck.py`, run by
`chart:lint` in CI) catches the same family of defects at the render
level, without a cluster. It is the fast lane; Calico is the truth.

## What lives only inside a cluster

A cluster is disposable, but these five things are not — they are not in
any repository, so a `minikube delete` destroys them:

| What | Where it comes from | How it is restored |
|---|---|---|
| The sealed-secrets controller key | generated by the controller on first start | the same Secret (same name, same `tls.crt`/`tls.key`) is put back — the committed SealedSecrets then decrypt again, with no re-seal |
| The Flux GitLab PAT (`flux-git-auth`) | a Personal Access Token with `read_repository` | captured as a Secret object, applied back |
| The GitLab Agent tokens | the GitLab UI (Project > Infrastructure > Kubernetes clusters) | captured, re-installed with the agent chart |
| The SOPS age key | `genie-ai-deploy/sops/<cluster>.age` on the operator's disk | `genie-ai-deploy/scripts/sops-install-cluster-secret.sh` (only for clusters that use SOPS — the laptop overlay does not) |
| The `selfsigned` cert-manager ClusterIssuer | applied off-chart | captured and re-applied |

The sealed-secrets key is the one that matters most: the ten
`SealedSecret` manifests in `genie-ai-deploy` are encrypted against it,
and they carry every real secret of the deployment (Arango credentials,
Keycloak client secrets, the vLLM API key, the translation cache
password). Losing it does not just lose the cluster — it invalidates the
committed manifests, and they would have to be re-sealed and re-committed.

### Restoring the sealed-secrets key

Two details make this work, and both fail silently if missed:

1. **The label.** The controller (0.40.0) selects its keys by the
   `sealedsecrets.bitnami.com/sealed-secrets-key=active` label, not by
   the name prefix. A key restored without that label is invisible: the
   controller logs `Searching for existing private keys`, finds nothing,
   **generates a fresh key**, and every committed SealedSecret then
   fails with `no key could decrypt secret`.
2. **The restart.** The controller reads its key set at startup. Restore
   the key, then restart `deploy/sealed-secrets-controller`.

Verify the restore before trusting it:

```bash
kubectl -n sealed-secrets logs deploy/sealed-secrets-controller \
  | grep "registered private key"
# registered private key secretname=sealed-secrets-keyXXXXX

kubectl -n genieai get sealedsecret -o json \
  | jq -r '.items[] | "\(.metadata.name) \(.status.conditions[0].status)"'
# every line must be True
```

## SealedSecret vs SOPS

Both encrypt a value before it reaches git. They are not
interchangeable, and this deployment uses them for different things.

| | SealedSecret | SOPS |
|---|---|---|
| Encrypted against | a key held by the cluster (sealed-secrets controller) | an age public key, the private half on the operator's disk |
| Decrypted by | the controller, in-cluster, at apply time | the Flux kustomize-controller, with a `sops-age` Secret in `flux-system` |
| What it carries here | the ten real runtime secrets (Arango, Keycloak, vLLM, Redis) | nothing yet — the pair stays in the repo as the template for a future cluster whose secret manager feeds the chart's values |
| Rotation | re-seal with `kubeseal` against the cluster | re-encrypt with `sops` |

**The laptop overlay does not use SOPS.** Its `secrets.template.yaml` /
`secrets.sops.yaml` pair only carries `REPLACE_ME` placeholders, and
the HelmRelease reads no `valuesFrom` Secret. The public values ride a
plain ConfigMap (`genieai-laptop-public`); the real secrets are the
SealedSecrets. The SOPS pair is deliberately left unwired — see
`overlays/jrevillard-laptop/dev/kustomization.yaml` in
`genie-ai-deploy`.

## Installation order

The order is not free: several steps need a namespace, a CRD or a
Secret that a later step creates.

```
1. minikube start --cni=calico        # the CNI decides whether the NPs apply at all
2. install-prereqs.sh                  # 7 cluster-wide operators (idempotent)
3. restore the sealed-secrets key      # BEFORE the controller unseals anything
4. restart the sealed-secrets controller
5. selfsigned ClusterIssuer            # cert-manager needs it before it issues the edge cert
6. flux install                        # creates the flux-system namespace + the Flux CRDs
7. restore flux-git-auth               # the PAT the source-controller reads the repos with
8. apply the GitRepository + the two Kustomizations
9. Flux reconciles → chart install → the SealedSecrets materialize
```

Steps 3 and 6 have bitten in practice, in opposite ways: the key must
exist before the controller tries to unseal anything, and `flux install`
must come before anything writes into `flux-system` (the namespace does
not exist before it).

Step 9 is where the deployment converges; the chart's own hooks
(`dep-check`, `clusterprofile-detect`, `db-migrations`, the Keycloak
convergence Job) run inside it.

## Running it

```bash
# 1. capture the cluster-only state BEFORE deleting the cluster — into
#    ~/.genieai-sealed-secrets, NOT the repo (the capture includes the
#    cluster's sealed-secrets PRIVATE key). The --capture mode is the
#    producer of exactly the files step 2 consumes — filename and file
#    shape are owned by the script, so they cannot diverge — and it
#    fails loudly when the active key is missing (an empty capture is
#    the silent path to a keyless cluster). NOT
#    `get secret sealed-secrets-key*`: a positional argument is an
#    exact-name selector in kubectl, not a glob; it silently matches
#    nothing.
mkdir -p ~/.genieai-sealed-secrets
./scripts/laptop-cluster-bootstrap.sh --capture ~/.genieai-sealed-secrets

# Rotation caveat — BEFORE the delete: if the controller ever rotated,
# SealedSecrets sealed with a rotated-out key must be re-sealed NOW
# (`kubeseal --re-encrypt` needs a controller holding both keys); the
# restore cannot revive a rotated-out key, and after the delete the old
# private key is gone for good. The --capture file is the ACTIVE key —
# the one the committed SealedSecrets are sealed with unless a rotation
# happened and was not re-sealed.

# 2. rebuild
minikube delete
./scripts/laptop-cluster-bootstrap.sh \
  --sealed-secrets-key ~/.genieai-sealed-secrets/sealed-secrets-key-active.json \
  --flux-git-auth ~/.genieai-sealed-secrets/flux-git-auth.json \
  --issuer ~/.genieai-sealed-secrets/selfsigned-issuer.yaml

# 3. the script never deletes a cluster — that stays a deliberate act
```

The script is idempotent: re-running it re-applies the operators and
the secret restores without touching the deployment.

## The laptop node is memory-tight

The chart gives the backend a 12 Gi memory limit, and it needs that
much: when the GPU translation endpoint is unreachable, the backend
falls back to an in-process CPU translation model
(`Xenova/nllb-200-distilled-600M`, 4 threads, 5 batches) whose ONNX
load peaks **above 8 Gi**.

The laptop node has 8 Gi in total. A GPU that blips — and the shared
GPU node does — therefore makes the backend load a model that cannot
fit: the container is OOMKilled (exit 137), and on a node that close to
its limit the OOM reaches the node too (the control plane dies with
it, and the cluster comes back with an empty etcd).

Two things follow for the laptop:

- keep the GPU translation endpoint reachable — the fallback is not
  survivable on an 8 Gi node;
- the node's own memory is the real constraint, not the pod's limit.

On a real cluster the 12 Gi limit is what keeps a GPU blip a degraded
translation instead of a backend outage.

## Validating the result

The six live checks, in order. The first four are HTTP; the last two
exercise the NetworkPolicy graph, which is the point of the Calico
cluster.

```bash
# 1. the edge answers
kubectl -n genieai port-forward svc/envoy-genieai-genieai-<hash> 4443:4443
curl -sk -H "Host: genieai.local" https://localhost:4443/api/health

# 2. the Keycloak theme is delivered (the login page carries genie.css)
# 3. the chat answers, with citations, over the whole RAG pipeline
# 4. a document uploads, is scanned by ClamAV and ingested by the dataprep
```

A quick check that the policies are not silently blocking anything:

```bash
kubectl -n calico-system logs ds/calico-node -c calico-node | grep -i deny
```

No output means no flow was refused.
