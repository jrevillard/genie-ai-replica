# Query Inspector

## Overview

The Query Inspector is an admin-only tool that provides full visibility into the RAG (Retrieval-Augmented Generation) pipeline for every user query. It allows administrators to inspect the complete lifecycle of a query — from the user's original question, through the payload sent to the OPEA RAG service, to the retrieved documents and final LLM response.

This is essential for:
- **Debugging retrieval quality** — seeing which documents were retrieved and their relevance scores
- **Auditing RAG behavior** — verifying that the correct context and labels are being sent
- **Monitoring confidence** — identifying low-confidence responses that may need knowledge base improvements
- **Reviewing user feedback** — correlating user satisfaction with pipeline behavior
- **Comparing LLM models** — tracking which model served each query, enabling side-by-side evaluation when testing different models (e.g., for the Lesotho deployment)

## Accessing the Query Inspector

The Query Inspector is available in the **Admin Dashboard** for users with the `AI Engineer` or `Admin` role. Navigate to the Admin panel and select the Query Inspector tab.

> **Note:** Users with the `Manager` role can access the Analytics dashboard and document management features, but cannot access the Query Inspector since it exposes private user query data.

## Features

### Query List View

The list view shows all answered queries with filtering and pagination:

| Column | Description |
|--------|-------------|
| Time | When the query was submitted |
| User Question | Truncated text of the user's question |
| Model | The LLM model used (e.g., `ibm-granite/granite-3.3-2b-instruct`) |
| Confidence | Confidence score from the RAG pipeline (color-coded) |
| Response Time | End-to-end response time in milliseconds |
| Sources | Number of documents retrieved from the vector DB |
| Feedback | User feedback rating (if provided) |

#### Filters

- **Search**: Full-text search across query text
- **Confidence Range**: Filter by minimum/maximum confidence score (0.0–1.0)
- **Date Range**: Filter by start/end date
- **User ID**: Filter queries from a specific user

### Query Detail View

Clicking "Inspect" on any query opens the full detail view with the following sections:

#### 1. 📝 User Question
The original question text, along with metadata:
- User name/ID
- Timestamp
- Response time
- Backend mode (e.g., `conversation-with-labels`, `single-message`)
- **LLM Model** — the model that generated the response (e.g., `ibm-granite/granite-3.3-2b-instruct`)

#### 2. 🏷️ Context (Labels sent to RAG)
The context labels that were active when the query was submitted:
- **Category**: The knowledge area category label
- **Service Labels**: Specific service/topic labels for filtering
- **Language**: The user's language preference

#### 3. 📡 RAG Request Payload (Sent to OPEA)
The **exact JSON payload** that was sent to the OPEA `/v1/chatqna` endpoint. This shows:
- **Endpoint**: The RAG service URL path
- **Mode**: The backend mode used for this query
- **Request Body**: The full JSON payload including:
  - `messages` — the conversation messages or single query string
  - `context` — category and service labels (in `conversation-with-labels` mode)
  - `user_id` — the user identifier
  - `stream` — whether streaming was requested

This section is critical for debugging because it shows exactly what the RAG system received, which may differ from the raw user input (e.g., in `single-message` mode, only the last message text is sent).

> **Note**: Queries processed before this feature was added will show "No RAG payload was recorded" — this is expected for historical data.

#### 4. 💬 Messages Sent to Pipeline
The full conversation message array that was stored with the query, showing each message's role (`user`, `assistant`, `system`) and content.

#### 5. 📚 Retrieved Documents (Vector DB Results)
The source documents returned by the vector similarity search:
- **Document name/ID**
- **Relevance score** (color-coded: green ≥0.8, yellow ≥0.5, red <0.5)
- **Category labels** on the document
- **Link to document** (if available)

#### 6. 🤖 LLM Response
The final response generated by the LLM, along with:
- Overall confidence score
- **LLM Model** used to generate the response (useful when comparing models during evaluation)

#### 7. ⭐ User Feedback
If the user provided feedback:
- Rating (thumbs up/neutral/thumbs down)
- Comment text
- Timestamp of when feedback was provided

## API Endpoints

### List Queries
```
GET /api/admin/queries/inspect
```

**Query Parameters:**
| Parameter | Type | Description |
|-----------|------|-------------|
| `limit` | integer | Max queries to return (default: 50) |
| `offset` | integer | Pagination offset |
| `userId` | string | Filter by user ID |
| `searchText` | string | Search in query text |
| `startDate` | string | Filter from date (ISO string) |
| `endDate` | string | Filter to date (ISO string) |
| `minConfidence` | number | Minimum confidence score (0–1) |
| `maxConfidence` | number | Maximum confidence score (0–1) |

**Response:**

### Get Query Details
```
GET /api/admin/queries/inspect/:queryId
```

**Response:**
Returns the full query document from the database, including all fields listed above plus:
- `userName` — resolved display name of the user (if available)
- `messages` — full conversation message array
- `sessionId` — the session in which the query was made
- `categoryId` / `serviceId` — resolved database IDs for the labels

## Architecture

### Data Flow

```
User submits query
    │
    ▼
Backend (query-service.js)
    ├── Stores initial query document in ArangoDB
    │     (text, messages, context, userId, sessionId)
    │
    ├── Constructs opeaPayload based on backend mode:
    │     • single-message: { messages: "last message text", stream: false }
    │     • conversation-with-labels: { messages: [...], context: {...}, user_id, stream: false }
    │
    ├── Sends payload to OPEA /v1/chatqna
    │
    ├── Receives response + metadata (source_documents, confidence_score)
    │
    └── Updates query document with:
          • response (LLM answer)
          • metadata (source docs, confidence)
          • ragPayload (exact payload sent to OPEA)
          • llmModel (model ID from VLLM_LLM_MODEL_ID env var)
          • responseTime
          • isAnswered: true
```

### Files

| File | Role |
|------|------|
| `components/gov-chat-backend/services/query-service.js` | Stores `ragPayload` in query document; serves inspector data |
| `components/gov-chat-backend/routes/admin-routes.js` | Admin API endpoints for Query Inspector |
| `components/gov-chat-frontend/src/components/QueryInspector.vue` | Vue component for the inspector UI |
| `components/gov-chat-frontend/src/components/QueryInspector.css` | Styles for the inspector panel |
| `components/gov-chat-frontend/src/services/adminDashboardService.js` | Frontend API client for inspector endpoints |

## Troubleshooting

### LLM Model shows "unknown" or "N/A"
The model name is read from the `VLLM_LLM_MODEL_ID` environment variable at query time. Ensure this variable is passed to the backend service in `docker-compose-t4.yaml`. After updating the compose file, rebuild the backend:
```bash
docker compose -f docker-compose-t4.yaml up -d --build backend
```

### "No RAG payload was recorded"
This appears for queries that were processed before the `ragPayload` field was added. Only new queries going forward will have this data.

### Empty source documents
If a query shows 0 retrieved documents, this could indicate:
- The knowledge base doesn't have relevant content for the query
- The category/service labels are filtering too aggressively
- The embedding model isn't matching the query to available documents

### Test mode queries
Queries processed in `test-mode` will have a `ragPayload` with a `_note` field indicating no actual RAG call was made. The payload shows what *would have been* sent.
