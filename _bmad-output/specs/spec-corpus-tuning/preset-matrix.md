# Preset Matrix — CAP-2 routing table

A closed-form lookup: `profile → recommended vars.yml baseline`. Hand-authored for v1 from team knowledge of GENIE.AI's existing deployments (El Salvador agri, Lesotho AI advisory, agrogenio generic). Empirically re-derived after 2-3 CAP-3 winners land.

## Input

A CAP-1 `corpus-profile.md` document.

## Output

A single YAML file containing the recommended baseline config (subset of `deploy/ansible/group_vars/<env>/vars.yml` keys). Reuses the same key names so the operator can paste it directly.

## Routing logic

The preset is selected along three orthogonal axes. Each axis narrows the recommended values.

### Axis 1 — corpus size

| Profile chunk count | RERANKING_STRATEGY | RERANKER_TOP_N | K | fetch_K |
|---|---|---|---|---|
| `< 5,000` | `slice` | 5 | 16 | 24 |
| `5,000 — 50,000` | `adaptive` (default) | 3 | 32 | 48 |
| `> 50,000` | `adaptive` | 3 | 48 | 64 |

Rationale: small corpora don't need adaptive cost-gating (signal/noise is clean); large corpora benefit from aggressive fetch with adaptive pruning.

### Axis 2 — language profile

| Multilingual? | Primary language | Embedding model | LLM | Translation model |
|---|---|---|---|---|
| `false` | `es` | `BAAI/bge-large-en-v1.5` (with caller-side query prefix) | `ibm-granite/granite-4.1-8b` | `Infomaniak-AI/vllm-translategemma-4b-it` |
| `false` | `en` | `BAAI/bge-large-en-v1.5` | `ibm-granite/granite-4.1-8b` | none |
| `false` | `fr` | `BAAI/bge-large-en-v1.5` | `ibm-granite/granite-4.1-8b` | `Infomaniak-AI/vllm-translategemma-4b-it` |
| `true` | any | `BAAI/bge-large-en-v1.5` | `ibm-granite/granite-4.1-8b` | `Infomaniak-AI/vllm-translategemma-4b-it` |
| `false` | `other` | `BAAI/bge-large-en-v1.5` | `ibm-granite/granite-4.1-8b` | `Infomaniak-AI/vllm-translategemma-4b-it` (lower confidence — manual review) |

Rationale: sovereign vLLM default; embedder is `bge-large` per project convention (MR !399, see [[default-embedding-bge-large]]). Translation model chosen when `multilingual = true` OR primary language is not English.

### Axis 3 — hardware + label density

| Hardware | Label density | LLM size | LABELING_STRATEGY | chunk_size |
|---|---|---|---|---|
| T4 (16GB, no bf16) | any | `ibm-granite/granite-3.3-2b-instruct` | `embedding` (default T4) | 1400 |
| A40 / RTX6000 (≥40GB, bf16) | `< 0.5` per chunk | `Qwen/Qwen2.5-7B-Instruct` | `embedding` | 1400 |
| A40 / RTX6000 (≥40GB, bf16) | `≥ 0.5` per chunk | `Qwen/Qwen2.5-7B-Instruct` | `llm` | 1400 |
| A40 / RTX6000 (≥40GB, bf16) | `≥ 1.0` per chunk | `Qwen/Qwen2.5-7B-Instruct` | `bm25` | 1400 |

Rationale: T4 cannot run 7B+ models reliably; LLM labeling is only viable when chunk labels are abundant enough to be worth the vLLM call cost.

## Output guarantees

- Lookup time: <1 second on commodity hardware.
- The output always contains a `# Operator review required` comment block at the top.
- The output never deploys itself — emitted to stdout or a path passed by `--output`, never to `vars.yml` directly.

## Failure modes

| Symptom | Likely cause | Suggested action |
|---|---|---|
| All three axes return their `default` row | Profile fields incomplete (e.g., `hardware_target` not provided) | Re-run CAP-1 with `--gpu-model` flag, or accept defaults + flag a warning |
| Empty recommended values for translation | Primary language detected but `multilingual=false` | Manual review; the recommendation assumes no translation cost |

## Versioning

The matrix is keyed by `profile.schema_version`. v1 of the matrix consumes v1 of the profile. Schema bumps require a matrix revision.

## Empirical derivation (post-v1)

After CAP-3 produces 2-3 winners, the matrix can be re-derived by clustering profile → winner configs. The hand-authored table is the v1 seed; empirical data refines it. Until then, the matrix is team knowledge.
