## 1. The exact configuration that was tested (live parameters)

These are the values the system used during the run — read from the live
`rag-tuning.json` (the file the services actually read at request time):

| Parameter | Value | What it does |
|---|---|---|
| `reranker.strategy` | **slice** | how the reranker picks the final context chunks |
| `reranker.topN` | **1** | slice keeps only the **single best-scored chunk** |
| `retriever.retrievalK` | 20 | how many candidate chunks the retriever hands to the reranker |
| `retriever.fetchK` | 30 | how many candidates hybrid search fetches before trimming |
| `retriever.scoreThreshold` | 0.2 | candidates below this similarity are dropped before the reranker |
| `retriever.hybridEnabled` | true (+BM25, RRF k=60) | search = vector similarity **and** keyword match, fused |
| `retriever.enableTraversal` | true (depth 2, max 5 returned, ≥0.7) | graph neighbors of good chunks can join the candidates |
| Contextual retrieval | on | every chunk carries an AI-generated "this document is about…" header |
| Embedding model | **BAAI/bge-m3** (TEI service) | converts text↔question to comparable vectors |
| Judge (RAGAS only) | **granite-4.1-8b** (local vLLM) | the local LLM that grades answer quality |

So one chat question travels: **embed → hybrid search (30) → trim (20 candidates) →
TEI cross-encoder scores all 20 → slice keeps the top 1 → LLM writes the answer grounded on it.**

## 2. Retrieval metrics — the numbers and what each means

| Metric | Value | Definition (plain words) |
|---|---|---|
| `retrieval_recall` | **1.000** | Of all the passages that *should* be findable, the fraction that made it into the 20 candidates **before** the reranker chose. 1.0 = the search step never loses the answer — everything the reranker needed was on the table. |
| `recall` (chunk-level) | **0.719** | Per question: of the gold chunks for that question, what fraction ended up **selected** (sent to the LLM). Because slice picks exactly one chunk, a question with 2 gold chunks can score at most 50% here. |
| `recall@1` | 0.719 | Same as recall here, stated as "the top-1 pick is a gold chunk" — happened on ~72% of questions. |
| `precision` | **0.857** | Of the chunks slice selected, the fraction that were actually gold. 0.86 = when slice picks, it almost always picks clean. (Not 1.0 because on ~3 questions the picked chunk was a wrong-but-plausible one.) |
| `noise` | 0.143 | The complement of precision: the fraction of selected chunks that were **not** gold — irrelevant baggage handed to the LLM. Low is good. |
| `passage_recall` | **0.702** | See section 3 — this is the one you asked about. |
| `complete_recall` | 0.595 | The fraction of questions where **100%** of the gold passages were selected. 25 of 42 questions got *everything* they needed. |
| `ndcg@1` | 0.857 | Ranking quality at position 1 (rewards putting the right chunk first; shares the precision value at k=1). |
| `ndcg@3/5/10` | 0.749–0.752 | Ranking quality deeper in the list — informational here, since slice only uses rank 1. |

## 3. Why passage recall is 0.702 — the full explanation

**Definition first.** Your gold dataset has **75 expected passages** spread over the 42
questions (some questions expect 1 passage, some expect 2–4). A passage is counted as
retrieved **only when every chunk that contains it was selected** — a half-retrieved
passage counts as not retrieved, because the LLM only saw part of the evidence.

**The arithmetic:** 52 of 75 passages were fully retrieved → per-question average = **0.702**.

**Why not higher — three separate reasons, all baked into the current setup:**

1. **Slice only ever picks ONE chunk (topN=1).** 28 of your 42 questions expect more
   than one gold chunk. Those questions are *mathematically capped* — one pick can
   never cover two passages. This is the single biggest cause.
2. **9 of the 75 passages are split across two chunks** (the chunker cut the passage
   mid-text when it built the ~4000-character chunks). A split passage needs BOTH
   chunks selected to count. With topN=1 that is impossible → those 9 fail automatically.
3. **The top-1 pick itself missed gold on ~12 questions** (recall@1 = 0.719) — the
   cross-encoder scored a different chunk higher. On this small, topically-overlapping
   corpus (three different files all discuss planting, for example) that's expected noise.

**The important context:** the *search* underneath is perfect (`retrieval_recall` = 1.000).
The 0.702 is not "the system can't find your answers" — it's "the picker only takes one
piece of them." This is exactly what the strategy comparison quantified: adaptive with
tuned parameters takes ~3.5 chunks and reaches 0.755 recall — but at 0.47 precision
(half of what it grabs is noise). **Chunk size (N.8, re-chunking to ~900 chars) fixes
reasons 1 and 2 at the root** by making passages small enough that one pick covers one
passage completely.

## 4. Answer quality — RAGAS (graded by the local granite judge)

RAGAS scores the **answers the system actually produced**, not just retrieval. The judge
 granite-4.1-8b read every question, the retrieved context, the system's answer, and
your reference answer.

| Metric | Value | Definition (plain words) |
|---|---|---|
| `faithfulness` | **0.874** | Do claims in the answer actually come from the retrieved context (vs. the LLM inventing)? 0.87 = answers are well grounded. 1 question produced no score (judge returned NaN). |
| `context_precision` | **0.976** | Was the retrieved context actually relevant to the question? 0.98 = slice almost never hands the LLM junk — consistent with noise = 0.14 above. |
| `context_recall` | **0.909** | Does the retrieved context contain the information your reference answer requires? 0.91 = the single picked chunk usually carries the needed facts. |
| `answer_relevancy` | 0.527 | Does the answer address the question as asked (measured by embedding similarity between answer and question)? 0.53 reads low but is typical for this metric — it punishes long, rounded advisory answers even when they're correct. The lowest faithfulness cases were the list questions (herbicide names), where answers enumerate many products. |

**Reading:** the pipeline is healthy end-to-end — search perfect, picks precise,
answers grounded. The weak spot is *coverage* (one chunk per answer), which is a
configuration choice, not a malfunction.

## 5. Caveats (honest limits of this run)

- 42 questions is a small sample — differences under ~10 points between configurations
  are not conclusive (the calibration bootstrap confirmed the top adaptive cells are
  statistically indistinguishable from each other).
- The corpus is the distilled handbook; after **N.8 re-chunking** (or any re-ingestion)
  these numbers must be re-measured — the recipe is proven and takes ~1 hour.
- `answer_relevancy` uses bge-m3 embeddings; its absolute value is metric-specific —
  compare it across runs, not against a "pass" bar.
- RAGAS judged the slice configuration (what users get today). The adaptive-tuned cell
  (0.755 recall) was replayed offline and has **not** been live-validated.
