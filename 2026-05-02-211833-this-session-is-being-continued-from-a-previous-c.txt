● This is a document quality problem causing LLM misattribution, not a retrieval
   failure. The right chunk was retrieved — the reasoning failed.

  What the LLM saw and why it chose wrong

  The Termite entry in the document reads:
  ## Termite
  - temperature Fogy and Cloudiness and abnormal high

  The Bacterial wilt entry reads:
  ## Bacterial wilt
  - High Night Temperature (28-30°C) and Relative Humidity(RH) 80-90%.

  The user said: "I have fog, cloudiness, and high temperature"

  Termite is the exact match. But the LLM picked Bacterial wilt for these
  reasons:

  1. The Termite description is malformed/OCR noise — "temperature Fogy and 
  Cloudiness and abnormal high" is grammatically broken. "Fogy" is a typo for
  "Foggy". It reads like a garbled extraction. The LLM's parser gives this lower
   semantic confidence than a cleanly-written entry.
  2. LLM adds conditions the user never gave — it answered "due to high night 
  temperatures (28-30°C) and relative humidity (80-90%)" — the user never
  mentioned RH or 28-30°C. The LLM hallucinated those from its training priors
  about bacterial diseases in hot weather. It anchored to the first entry that
  matched "high temperature" with specific, authoritative-sounding numbers.
  3. Training bias — In LLM training data, "fog + high temperature" in tropical
  agriculture is heavily associated with bacterial/fungal diseases. The model's
  prior knowledge overrides the retrieved document when the document is poorly
  written.
  4. It explicitly contradicted itself — It said "There is no specific mention 
  of Termite" — but Termite IS in the same chunk, on the very next line. The
  broken formatting made the LLM discount it as not a proper condition
  description.

  Fix

  There are two places to fix this:

  Fix 1 — Fix the source document (the real root cause)

  The Termite entry needs to be rewritten in the same clean format as the
  others:

  ## Termite
  - Foggy and cloudy weather with abnormally high temperature.

  This is the most important fix. Once the document chunk has consistent,
  readable format, the LLM will match it correctly. The current text
  "temperature Fogy and Cloudiness and abnormal high" reads like a table row
  that was scraped incorrectly.

  Fix 2 — Add a systematic matching instruction to the system prompt

  Add this to CHATQNA_SYSTEM_PROMPT in .env:

  When listing pests or diseases based on weather conditions, go through each
  entry in the retrieved document systematically and check each condition
  against what the user reported. List ALL entries whose conditions match. Do
  not infer conditions the user did not mention.

  This prevents the LLM from hallucinating RH values and anchoring to the first
  partial match it finds.

  ---
  The retrieval pipeline is working correctly. The problem is entirely in the
  source document having inconsistent/broken text for the Termite entry. Fix the
   document, re-ingest it, and the answer will be correct.

  What the documentation says

  The README (genie-ai-overlay/dataprep/README.md) lists the supported formats

  JSON is not mentioned anywhere in the documentation — not in the features

  simply not a supported format.

  However, the README does have a deliberate extension point at lines 636–659
  titled "Adding New Document Formats":

  class CustomExtractor(BaseExtractor):
      def extract(self, file_path: str) -> str:
          # Implementation
          pass

  EXTRACTORS = {
      ".custom": CustomExtractor()
  }

  This is the designed pattern for adding a new format. JSON is implicitly
  handled by this mechanism — it was never included, but the architecture
  explicitly anticipates someone adding it.

  ---
  The silent blocker the docs don't warn you about

  Even if you bypassed the missing loader, genieai_dataprep_utils.py:186 would
  drop the chunks silently:

  readable_chars = sum(1 for char in chunk if char.isalnum() or char.isspace())
  if len(chunk) > 0 and readable_chars / len(chunk) < 0.7:
      return False  # dropped

  A raw JSON chunk like {"id": "climate_cotton_bogura_w27", "text": "Crop: 
  cotton..."} has {, ", :, , pushing the non-alphanumeric ratio above 30% →
  silently dropped. You'd ingest nothing and get no error.

  But — and this is important — the text field VALUE alone (e.g. "Crop: cotton |
   Region: bogura | Week 27 | Climate: Rainfall 93.0mm, Temp 26.0-32.0°C")
  passes the filter fine. The ratio on the text string itself is well above 0.7.
   The problem is only when the raw JSON structure wraps it.

  ---
  What this means for your decision

  The documentation points to a clean implementation path: add a JSONExtractor
  following the documented pattern that:
  1. Reads the .json file
  2. Extracts only the text field from each record (skips the structural JSON)
  3. Optionally stores the metadata fields as ArangoDB chunk attributes
  4. Returns the list of text strings — which already pass is_valid_content()

  The text field in your Pydantic records is already natural language formatted
  precisely for this purpose. The only thing missing is a 30-line extractor
  class and a registration in _load_and_chunk. The is_valid_content blocker is
  not a fundamental constraint — it's an artefact of reading JSON as raw text
  instead of parsing it.

● There are two distinct problems happening simultaneously. Let me diagnose each
   precisely.

  ---
  Problem 1: Wrong answer (October instead of November)

  The correct answer is November — Weeks 45, 46, 47 are all "Vegetative Growth".
   The LLM answered October.

  Look at what was retrieved: Chunk 0 — the document title chunk containing Week
   42 (Spouting) and the header of Week 43. This chunk scores highest with the
  reranker because it contains every relevant keyword: "Crop Weather Calendar",
  "Potato", "Dhaka Region". The query "vegetation growth of potato in dhaka"
  matches the document header strongly via embedding similarity, regardless of
  the actual stage values inside.

  Chunks 2, 3, 4 — which contain the actual "Stage: Vegetative Growth" entries —
   are dominated by numerical weather data (rainfall, temperature, RH, wind).
  Their embeddings are pulled toward weather/meteorology signal, not crop stage
  signal. The phrase Stage: Vegetative Growth is just one line among 10
  numerical attributes. It doesn't win the embedding competition.

  Root cause of wrong answer: The document title in Chunk 0 matches the query
  better than the stage field buried in numerical chunks.

  ---
  Problem 2: Hallucinated data (Week 43 shows Week 42's values)

  Look at the chatbot response closely — it shows Week 43 with these values:
  Rainfall: 40.5 mm, Min Temp: 23.8°C, Stage: Spouting

  That is Week 42's data, not Week 43's. Week 43 should be Rainfall: 26.0mm, Min
   Temp: 22.3°C, Stage: Seedling.

  Now look at Chunk 0 vs Chunk 1:

  CHUNK 0 ends with:
    ## October - Week 42
    - Rainfall: 40.5 mm ... Stage: Spouting
    ## October - Week 43        ← header appears, NO DATA follows

  CHUNK 1 starts with:
    ## October - Week 43
    - Rainfall: 26.0 mm ... Stage: Seedling

  The RecursiveCharacterTextSplitter cut the text at a character boundary that
  landed exactly after the ## October - Week 43 header, before any of its data.
  The overlap setting then carried the Week 43 header into Chunk 0's tail. The
  LLM sees: "Week 42 data, then a Week 43 header with nothing after it" — so it
  fills in Week 43's data by repeating Week 42's values. That is a hallucination
   caused by the chunk cut.

  ---
  Root cause of both problems: chunk size relative to section size

  Each week section in outpud_refined.md is approximately 180–200 characters.
  The default chunk size for .md files is much larger (likely 500–1000 chars),
  so each chunk spans 2–3 weeks and cuts mid-section. This causes:

  1. Sections split across two chunks → LLM sees incomplete sections →
  hallucination
  2. Each chunk is diluted with multiple weeks of numerical data → stage-based
  semantic signal is weak → wrong chunk retrieved for stage queries

  The fix is to reduce the chunk size for this document to ~200 chars so each
  week gets its own chunk, OR better — use a Markdown header splitter that
  splits at ##  boundaries, giving exactly one chunk per week regardless of
  character count.

  Chunk 0 should be:
  # Crop Weather Calendar - Potato (Dhaka Region)
  ## October - Week 42
  Rainfall: 40.5mm ... Stage: Spouting

  Not a heading spanning into the next week with no closing data.

  ---

  ---
  One edge case to handle

  MarkdownHeaderTextSplitter doesn't enforce a max size — a section with a long
  prose block (a legal document, a detailed advisory) could produce a
  10,000-character chunk. The safe pattern (same one used in OPEA for Excel) is
  a secondary pass:

  elif path.endswith(".md"):
      md_splitter = MarkdownHeaderTextSplitter(
          headers_to_split_on=[("#", "H1"), ("##", "H2"), ("###", "H3")],
          strip_headers=False
      )
      md_docs = md_splitter.split_text(content)
      # Secondary split for any section that exceeds chunk_size
      secondary = RecursiveCharacterTextSplitter(
          chunk_size=doc_path.chunk_size,
          chunk_overlap=doc_path.chunk_overlap,
          separators=get_separators(),
      )
      docs = secondary.split_documents(md_docs)

  This way: structured markdown (crop calendars, weekly data) → one chunk per ##
   section. Long prose markdown → further split by character count as fallback.
  Best of both worlds, works for any markdown regardless of content type.

● The chunks are structurally correct now — one per week, no splits. But there's
   a new problem introduced by the splitter itself. Look at the chunks
  carefully:

  Every week chunk contains zero context about crop or region.

  CHUNK 4:
  ## November - Week 45
  - Rainfall: 10.0 mm
  ...
  - Stage: Vegetative Growth

  The # Crop Weather Calendar - Potato (Dhaka Region) title only appears in
  Chunk 0. MarkdownHeaderTextSplitter moves parent headers into chunk metadata,
  not into the text of child chunks. So when the query asks about "vegetative
  growth of potato in dhaka", none of the weekly chunks embed those words —
  their text is just "November - Week 45 + weather numbers". The vector search
  matches whatever has "potato"/"dhaka" in text, which is only Chunk 0 (the
  title chunk). Everything else retrieves by weather signal alone.

  That's why confidence is 1% — the reranker correctly scores retrieved chunks
  as nearly irrelevant because the numerical weather chunks don't match a
  crop-stage query.

  The fix is to prepend the H1 context from metadata back into each child
  chunk's text after splitting:
