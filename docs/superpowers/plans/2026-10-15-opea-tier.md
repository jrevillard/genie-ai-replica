# Phase 3 — Tier OPEA Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Render the OPEA orchestrator tier (chatqna, retriever, dataprep, reranker, embedding, translation) in genieai-umbrella with the GPU backend as a binary values choice (external API vs in-cluster models), restoring the RAG pipeline (chat + ingestion) on Kubernetes.

**Architecture:** Compose topology preserved (decision 2026-10-15, Phase 3 section of `2026-10-13-chart-installable-phase1.md`). Orchestrators are in-cluster Deployments behind the existing nginx edge; model endpoints (vLLM/TEI/docling) resolve either to an external GPU node (mode `external`) or to in-cluster gpu-models Deployments (mode `in-cluster`, nodeSelector `gpu=true`). Same orchestrator templates both ways — only the endpoint values differ.

**Tech Stack:** Helm 3 (existing service factory), genie-ai-* images from the CI registry (16-image set), upstream `opea/translation:1.3` from docker.io.

**Spec:** `docker-compose.yaml` services (profile `opea`) are the parity reference — env names, defaults, and dependency edges come from there verbatim.

## Global Constraints

- Every env var below carries its **compose default** unless the table says otherwise; compose defaults are copied verbatim, not reinvented.
- In-cluster URLs use the chart's Service names (`chatqna.genieai.svc.cluster.local` style), derived from `.Values.namespace` — no hardcoded namespaces.
- GPU endpoint URLs derive from `opea.gpu.nodeHost` + path map in `external` mode; from in-cluster Service names in `in-cluster` mode.
- Secrets are referenced, never rendered: `arango-root-secret` (username/password), `kc-dataprep-client-secret` (KC_DATAPREP_CLIENT_SECRET), `vllm-api-key` (VLLM_API_KEY, HF_TOKEN), `keycloak-admin-credentials`.
- `OPEA_SSL_SKIP_VERIFY=1` when `opea.gpu.nodeHost` starts with `https://` and no CA is configured (self-signed GPU node, same rationale as backend NODE_TLS).
- The whole tier is gated by `opea.enabled: false` — rendering nothing by default.
- No `#` comments inside Helm `list (...)` actions (parse error); wrap comment blocks outside expressions.
- Comments factual, no history, no story refs.

## Values surface

```yaml
opea:
  enabled: false
  gpu:
    mode: external                # external | in-cluster
    nodeHost: ""                  # external mode: e.g. https://10.0.0.110:444
    paths:                        # appended to nodeHost (env §14 conventions)
      llm: /llm
      embedding: /embed
      reranker: /rerank
      translation: /translation
      docling: /docling
  # Tuning blocks carry compose defaults; each service template maps them 1:1.
  chatqna: {}                     # RERANKING_*, RETRIEVER_ARANGO_*, MULTI_TURN_*, CONFIDENCE_*, prompts
  retriever: {}                   # RETRIEVER_*, hybrid BM25 knobs
  dataprep: {}                    # chunk sizes, LABELING_*, CONTEXTUAL_*
  reranker: {}                    # NOVELTY_SIGMOID_*, CONTEXT_DECAY_FACTOR, MIN_VALUE_THRESHOLD
  embedding:
    modelId: BAAI/bge-large-en-v1.5
  translation:
    modelId: google/gemma-3-4b-it
  models:                         # in-cluster mode only (gpu-models parity)
    llm: { modelId: meta-llama/Meta-Llama-3.1-8B-Instruct }
    resources: {}                 # vLLM/TEI requests/limits
```

## Tasks

### Task 1 — values + endpoint derivation helper
Create `templates/_lib/_opea.tpl`: `genieai-umbrella.opeaGpuEndpoint` (path key → full URL per mode) and `genieai-umbrella.opeaSslSkipVerify`. Add the `opea:` values block. Gate: `helm template` with `opea.enabled=false` renders zero new resources.

### Task 2 — embedding + reranker + translation
Three Deployments+Services via the existing service factory. Images: `genie-ai-embedding` / `genie-ai-reranker` (registry, tag `main`), `docker.io/opea/translation:1.3` (not mirrored — same treatment as kcc/ArangoDB). Env tables above.

### Task 3 — retriever
Deployment+Service; arango wiring mirrors backend; tuning env from `opea.retriever`.

### Task 4 — dataprep
Deployment+Service; full table above; KC dataprep credentials via secretKeyRef.

### Task 5 — chatqna + backend OPEA_HOST
Deployment+Service; wiring table above. Set overlay `services.backend.opeaHost` to the chatqna Service DNS (chat stream path becomes live).

### Task 6 — mode `in-cluster` gpu models
Templates gated on `opea.gpu.mode=in-cluster` for vllm/tei/tei_reranker/vllm-translation with nodeSelector and resource values. Not validated on the laptop (no GPU) — render-time assertions only; live validation deferred to a GPU cluster.

### Task 7 — nginx route + NetworkPolicies
nginx: no new route needed (backend proxies the chat stream — verify `OPEA_HOST` path flows through `/api/*`). NetworkPolicies per service following the existing default-deny pattern (DNS + in-cluster peers + egress to GPU node when external).

### Task 8 — secrets + overlay (laptop)
Deploy repo: `huggingface-token` decision (reuse `vllm-api-key` key family or new SealedSecret), overlay sets `opea.enabled: true`, `gpu.mode: external`, `nodeHost: https://10.0.0.110:444`.

### Task 9 — render guard + validation
- Render-time assertion: every env row in each OPEA template has a source (extend the pattern used by the convergence Job guard).
- Cluster validation (laptop, external GPU): healthcheck endpoints per service, doc ingestion through doc-repo → dataprep (ArangoDB chunks appear), chat query through backend → chatqna → streaming answer. GPU endpoints reachable from pods (the .110:444 probe pattern).
