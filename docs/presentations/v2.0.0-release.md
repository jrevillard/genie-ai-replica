# Security &amp; Identity

## Zero-trust architecture and authentication overhaul

---

# Security Hardening

<div class="eyebrow">15 dedicated fixes — non-negotiable upgrades from R_1_0_0</div>

<div class="columns">
<div>

**Access Control**
- Auth bypass on `/email` route fixed — all routes now enforce authentication
- Admin authorization on every DB operation — role-based via Keycloak, no hardcoded bypass
- JWT claims replace stale cached roles — permission changes take effect immediately

**Injection Prevention**
- **AQL injection** eliminated — all queries use tagged template literals
- **Shell injection** eliminated — `exec()` replaced with Node.js built-in APIs
- **CRLF injection** — Content-Disposition headers sanitized

</div>
<div>

**Data Protection**
- **Path traversal** hardened — file upload, storage, log operations
- **Magic-byte validation** — files checked by content, not MIME type
- **No hardcoded secrets** — JWT + DB password fail fast if missing
- **No error leakage** + **array size limits** on batch endpoints

</div>
</div>

<div class="ops-benefit"><strong>Operational Benefit:</strong> Server fails fast on missing secrets instead of silently falling back to insecure defaults. No configuration needed — all 15 fixes are code-level and activate automatically on upgrade.</div>

---

# Keycloak OIDC Authentication

<div class="eyebrow">Identity Provider Migration</div>

<div class="columns">
<div>

**What changed**
- Legacy auth **fully replaced** by Keycloak — central IdP for web, mobile, API
- Standard OIDC (Authorization Code + PKCE), SSO, self-service password reset

**Mobile app**
- Flutter OIDC with build flavors, custom URL schemes, TLS enforcement

</div>
<div>

**Before & After**

| R_1_0_0 | v2.0.0 |
|---------|--------|
| Custom auth code | Keycloak OIDC |
| No password reset | Self-service reset |
| Hardcoded role logic | Keycloak roles + groups |
| Token stored in-app | Standard OIDC tokens |

</div>
</div>

<div class="ops-benefit"><strong>Operational Benefit:</strong> Industry-standard protocol reduces maintenance burden. Integrates with existing IdP infrastructure (AD, LDAP, external OIDC). Custom auth code eliminated — fewer lines to audit, fewer bugs to fix.</div>

# Faster Document Ingestion

<div class="eyebrow">Batched LLM labeling — 10× speed improvement</div>

<div class="columns">
<div>

### R_1_0_0 → v2.0.0
- **Before:** 1 chunk per API call, concurrency 5 — 50 min/document. No progress visibility.
- **After:** 4 chunks per call, adaptive concurrency — ~5 min/document. Per-chunk `ingestion_log` visible in admin panel.
- Alternative: `LABELING_STRATEGY=embedding` skips LLM labeling entirely when speed > label precision.

</div>
<div>

### Performance Impact

| Metric | R_1_0_0 | v2.0.0 |
|--------|---------|--------|
| Chunks per API call | 1 | 4 |
| Typical 50-page PDF | ~50 min | ~5 min |
| Progress visibility | None | Per-chunk log |

</div>
</div>

<div class="ops-benefit"><strong>Operational Benefit:</strong> Order-of-magnitude faster ingestion without adding GPU capacity. Label scoping eliminates cross-document contamination. Per-chunk progress visible in admin panel via `ingestion_log`.</div>

---

# Contextual Retrieval

<div class="eyebrow">Anthropic-style document understanding — enabled by default</div>

<div class="columns">
<div>

**How it works**
1. Before embedding, an LLM reads each chunk and generates a **context prefix**
2. Context explains the chunk's role: "This table lists soil pH requirements for tomato cultivation..."
3. Context is prepended **for embedding only** — labels stay on raw text for precision

**What this means for users**
- Domain-specific documents retrieved with **higher relevance**
- A table row about "pH 6.2" is understood as agricultural data, not chemistry

</div>
<div>

**Configuration** — `CONTEXTUAL_RETRIEVAL_ENABLED=true` (default). Model, max_tokens, strategy, and label_raw all configurable per deployment via `.env`.

</div>
</div>

<div class="ops-benefit"><strong>Operational Benefit:</strong> Enabled by default — no action needed. Costs ~1 extra LLM call per chunk at ingest time, substantially improves retrieval precision. Disable per deployment if ingestion speed is the absolute priority.</div>

---

# Reranking Strategies

<div class="eyebrow">Five configurable strategies — no redeploy needed</div>

<div class="columns">
<div>

### Five Strategies (`RERANKING_STRATEGY`)

The reranker scores and ranks candidate documents by relevance. Only top results reach the LLM — bad reranking = wrong answer.

| Strategy | Behavior | Best For |
|----------|----------|----------|
| `slice` | Top-N | General use |
| `threshold` | All above cutoff | High-recall |
| `slice_threshold` | Top-N above threshold | Mixed-quality docs |
| `knee_threshold` | Auto-detect drop-off | Unknown distributions |
| `adaptive` | Self-calibrating (default) | Production, hands-off |

`RERANKER_TOP_N` controls N. Switch at runtime via env var — no redeploy.

</div>
</div>

<div class="ops-benefit"><strong>Operational Benefit:</strong> Runtime-configurable via env var. Switch strategies without touching code or restarting services. Each deployment tunes for its own document quality profile.</div>

---

# Streaming: Translation &amp; SSE

<div class="eyebrow">Real-time responses, no "translate after generation" lag</div>

<div class="columns">
<div>

### Streaming Translation
- Chat output streams **in the target language** during generation
- R_1_0_0: English response generated first, then translated — users waited twice
- v2.0.0: AST-preserving markdown translation — formatting survives the translation step
- Toggle: `STREAMING_TRANSLATION_ENABLED`

**Impact:** Multilingual deployments feel native-speed, not "English with a translation delay."

</div>
<div>

### SSE Streaming
- LLM responses stream via **Server-Sent Events** — tokens appear as they're generated
- Replaces R_1_0_0's full-response wait, works with both monolingual and translated responses

**Combined effect:** R_1_0_0 generates English first, then translates — users wait twice. v2.0.0 streams the target language directly during generation.

</div>
</div>

<div class="ops-benefit"><strong>Operational Benefit:</strong> Perceived responsiveness dramatically improved for multilingual deployments. Streaming translation eliminates the double-wait; SSE eliminates the "spinner of doom" for all users regardless of language.</div>

---

# Multi-Turn Conversations &amp; Abstention

<div class="eyebrow">Smarter dialog, safer answers</div>

<div class="columns">
<div>

### Multi-Turn Vector Blending
- Previous turns blended with current query: α·E<sub>Q</sub> + (1−α)·E<sub>H</sub>
- "What about tomatoes?" after discussing irrigation → retrieves tomato irrigation docs, not generic
- Toggle: `MULTI_TURN_BLEND_ENABLED`

</div>
<div>

### RAG Abstention
- Assistant says **"I don't know"** instead of hallucinating — configurable confidence threshold

| Scenario | R_1_0_0 | v2.0.0 |
|----------|---------|--------|
| Docs found, relevant | Answers correctly | Answers correctly |
| Docs found, irrelevant | Fabricates | Abstains |
| No docs found | Fabricates | Abstains |

> Toggle: `CHATQNA_ENFORCE_ABSTENTION`

</div>
</div>

<div class="ops-benefit"><strong>Operational Benefit:</strong> Multi-turn + abstention together reduce support tickets. Users get contextual follow-up answers, and the assistant admits ignorance rather than fabricating — critical for public-sector deployments where incorrect information has regulatory consequences.</div>

# GPU Deployment

<div class="eyebrow">Flexible AI infrastructure — local or remote</div>

<div class="columns">
<div>

### Local GPU
- NVIDIA GPU utilization and data type **configurable per deployment**
- GPU-specific env files: `env.t4` (16 GB), `env.rtx6000` (24 GB)
- Memory utilization, model length, sequence limits tuned per GPU
- Any OpenAI-compatible vLLM endpoint — embedding + reranker + translation models configurable independently

</div>
<div>

### Remote GPU Node
- Deploy model services on a **dedicated GPU machine** — no GPU slot needed on main server
- TLS-encrypted communication between CPU and GPU nodes
- API key authentication (`VLLM_API_KEY`)
- Orchestrator endpoints overridden to GPU node host

```
CPU Node (app services) ──TLS──▶ GPU Node (vLLM, TEI)
```

</div>
</div>

<div class="ops-benefit"><strong>Operational Benefit:</strong> GPU can be a separate machine — air-gapped deployments supported. CPU-only translation fallback when no GPU is present. GPU config files isolate hardware-specific tuning from the main env file.</div>

# OpenTelemetry Tracing

<div class="eyebrow">End-to-end visibility across 8+ services</div>

<div class="columns">
<div>

### RAG Pipeline — Every Hop Traced

`Browser → Kong → Backend → ChatQnA → {Embedding, Retriever, Reranker, LLM, Translation}`

W3C `traceparent` propagates context across every service boundary. Instrumented in **Node.js** (Express + ArangoDB queries), **Python** (FastAPI + RAG stages), **Kong** (gateway plugin). PII auto-filtered from span attributes.

</div>
<div>

### What Traces Answer
- **Per-phase duration** — which RAG stage is slow?
- **Retriever span** — what documents were found?
- **Reranker scores** — how were they ranked?
- **ChatQnA span** — what prompt reached the LLM?
- **Error attributes** — where exactly did it fail?

Configuration: `ENABLE_OBSERVABILITY=0` (off by default, zero overhead), `OTEL_TRACES_SAMPLER_RATE=100.0`, `OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318`

</div>
</div>

<div class="ops-benefit"><strong>Operational Benefit:</strong> Disabled by default — zero overhead. Enable with one flag. Traces propagate automatically via W3C headers — no per-service code changes. PII auto-filtered before export.</div>

# Key Changes for Deployers

<div class="eyebrow">Actions required when upgrading from R_1_0_0</div>

| Area | Change | Action |
|------|--------|--------|
| **Auth** | Legacy auth → Keycloak OIDC | Provision Keycloak realm, clients, users. Set `KEYCLOAK_*` env vars |
| **Config** | New required variables | Add `KEYCLOAK_*`, observability, and GPU variables to `.env` |
| **Secrets** | No hardcoded fallbacks | Ensure `JWT_SECRET`, `ARANGO_PASSWORD` are set (server fails fast if missing) |
| **Deployment** | Manual → Ansible | Set up Ansible inventory. Configure `ansible-vault` for secrets |
| **GPU** | New GPU config files | Review `env.t4` / `env.rtx6000` for your hardware |
| **Data** | Schema compatible | No migration needed for existing ArangoDB collections |

<div class="ops-benefit"><strong>Recommendation:</strong> Deploy v2.0.0 as a fresh stack, then migrate data. The auth system change makes in-place upgrades complex. Ansible playbook handles the entire fresh deployment in one command.</div>
