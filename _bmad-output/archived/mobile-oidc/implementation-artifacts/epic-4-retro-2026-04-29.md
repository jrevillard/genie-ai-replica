## Epic Summary

Epic 4 focused on enabling multi-institution deployments: each institution gets its own build identity (app ID, bundle ID, signing config), a dedicated Keycloak OIDC client, and a custom URL scheme for OIDC callbacks. A comprehensive deployment onboarding guide ties it all together.

## What Went Well

### 1. iOS Build System Completeness (Story 4.1)

The full iOS flavor system was implemented from scratch: 12 XCConfig files, 12 project-level + 12 target-level + 12 test-level build configurations in `project.pbxproj`, 4 Xcode schemes, Podfile mapping, and Info.plist variable substitution. All done without Xcode GUI — manual pbxproj editing. This is a non-trivial achievement.

### 2. keycloak-config-cli Automation (Story 4.2)

Adding the mobile OIDC client to `genie-realm.yaml` with `$(env:VARIABLE)` substitution means operators never touch the Keycloak admin console. The env var passthrough to the `keycloak-config` service in `docker-compose.yaml` (Swarm constraint) was correctly identified and implemented.

### 3. Cross-Flavor Runtime Verification (Story 4.3)

Building two APKs (itu + dev), installing them on the same emulator, and confirming that each URL scheme routes to the correct app — this is real evidence that the multi-deployment architecture works. The `adb shell am start` test for cross-flavor routing is conclusive.

### 4. Scheme Coherence Rule Documentation (Stories 4.2, 4.4)

The 5-layer coherence rule (Dart config, Gradle, XCConfig, env, Keycloak redirectUris) was identified as the single most critical deployment invariant and documented exhaustively across Dev Notes, env template comments, and the deployment guide. A mismatch causes silent OIDC callback failure — this risk is now well-communicated.

### 5. Comprehensive Deployment Guide (Story 4.4)

11 sections covering the complete operator journey: env vars, Keycloak client, scheme coherence, flavor configuration (4-layer checklist), Android signing, build, validation, air-gapped deployments, OS version policy, app store submission, rollback, and troubleshooting. References existing docs rather than duplicating content.

## Challenges

### 1. Manual iOS Build Configuration is Error-Prone (Story 4.1)

Editing `project.pbxproj` by hand (36 build configurations, 12 PBXFileReference entries, 3 XCConfigurationList updates) is fragile. The review caught 2 issues: inconsistent `ASSETCATALOG_COMPILER_GENERATE_SWIFT_ASSET_SYMBOL_EXTENSIONS` values and missing `key.properties` fallback for release builds. Without Xcode GUI, these errors are hard to spot.

**Impact:** Medium. Any future flavor addition requires the same manual pbxproj editing. Risk of introducing inconsistencies grows with each new deployment.

### 2. Documentation Precision Gaps (Story 4.3)

6 review patches on a verification/documentation story — the highest in the epic. Issues included: missing `-t` and `--dart-define` flags in build commands, hardcoded `ANDROID_HOME` path, imprecise glob patterns (`*.xcconfig` matching base files), missing expected output annotations, and missing `plutil`/`unzip` commands for iOS inspection.

**Lesson:** Documentation stories need the same rigor as code stories. "Obvious" commands like `flutter build apk --flavor itu` are only obvious if you know the exact flag combination.

### 3. Deferred Items Accumulation (All Stories)

15 items deferred across 4 stories. Most are pre-existing limitations or out-of-scope improvements:
- No automated enforcement for scheme coherence rule (3 stories flagged this)
- No backchannel logout configuration
- No `webOrigins` in Keycloak mobile client
- Non-flavored debug build collides with `itu` flavor
- `e2e_config.dart` missing `allowInsecureConnections: true`
- Various documentation improvements (DNS examples, health checks, permissions, compliance)

**Concern:** These deferred items are low-severity individually but represent a growing tail of "known but unaddressed" issues. Epic 6 (Legacy Removal & Security Hardening) would be the natural place to batch-address them.

### 4. Zero Automated Tests (Epic-wide)

No unit tests, no integration tests, no CI verification. The entire epic relies on:
- `flutter analyze` (static analysis only)
- Manual APK builds (regression check)
- Manual emulator verification (Story 4.3 only)

Build infrastructure is inherently harder to test, but the scheme coherence rule — the most critical invariant — has zero automated enforcement. A future developer adding a new deployment could mismatch the scheme across layers and only discover it at runtime.

### 5. Swarm Constraint: Manual Env Var Passthrough (Story 4.2)

`docker stack deploy` ignores `env_file` for `keycloak-config` service. Each new env var in `genie-realm.yaml` must be manually added to the `environment:` block in `docker-compose.yaml`. This was correctly identified and implemented, but it's a process trap — forgetting this step causes silent keycloak-config-cli failure.

## Key Takeaways

1. iOS build infrastructure without Xcode GUI is possible but fragile — pbxproj editing requires extreme attention to detail and benefits from scripted verification
2. The scheme coherence rule is the single most critical deployment invariant — it crosses 5 config layers and a mismatch causes silent OIDC failure with no error message
3. Documentation stories are not "easier" than code stories — imprecise commands, missing flags, and wrong paths cause real operator friction
4. Deferred items accumulate silently — 15 items across 4 stories is manageable, but the pattern will compound if not addressed in Epic 6
5. keycloak-config-cli automation (`$(env:VARIABLE)` substitution) eliminates manual Keycloak console work — this is a significant operator productivity gain
