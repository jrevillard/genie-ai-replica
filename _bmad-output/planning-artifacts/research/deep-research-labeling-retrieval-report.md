# Document-Context-Aware Labeling & Retrieval for GENIE.AI RAG

A Research Report for the GENIE.AI Team

---

## 1. Executive Summary

GENIE.AI's per-chunk labeling pipeline produces high-quality labels for the ~1/3 of chunks that explicitly mention the document's subject, but misses document-level context for the remaining ~2/3. The cucumber cultivation guide case study (11/34 chunks labeled "Cucumber") is the canonical symptom: chunks about generic techniques (pest control, planning) are correctly labeled for the technique but lose the document's subject identity, causing label-filtered retrieval to silently drop most of a relevant document.

**Five key takeaways:**

1. **The file_labels merge is the #1 quick win** — zero LLM cost, trivially implementable, directly solves the observed problem. GENIE.AI already fetches `file_labels` (document metadata labels) but does not propagate them to chunk-level labels. Merging them guarantees every chunk in a document carries the document's subject labels.

2. **Contextual Retrieval (Anthropic) is proven but its headline 49% failure-reduction figure does not generalize.** An independent benchmark on financial text-and-table documents found only +2.8pp Recall@5 — "consistent moderate gains at one-time cost," ranked third priority behind hybrid fusion and reranking. The technique requires one LLM call per chunk, which is the cost profile GENIE.AI actively moved away from.

3. **Late Chunking (Jina AI) produces context-aware embeddings with zero LLM calls** — it runs the entire document through a long-context embedding model, then pools per-chunk boundaries. However, it requires switching to a long-context embedding model (>=8192 tokens), and all evaluations are English-only with no Spanish or cross-lingual validation — a material risk for GENIE.AI's multilingual deployment.

4. **Query-time LLM expansion (HyDE) is counterproductive for domain-specific queries** — it underperforms even vanilla dense retrieval (R@5=0.544 vs 0.587) because hallucinated plausible-but-wrong content pulls the query embedding away from true relevant context. GENIE.AI should avoid this class of technique.

5. **BM25 remains strong for domain-specific corpora** — outperforming a state-of-the-art dense model (OpenAI text-embedding-3-large, 3072 dims) on financial text across all metrics except R@20. This supports maintaining a lexical/hybrid component for GENIE.AI's domain-specific service-category taxonomy, though ArangoDB's native hybrid view already provides this.

**#1 Recommended next step:** Implement the file_labels merge in dataprep (estimated <1 day effort, zero additional LLM cost), then measure the before/after label coverage on the cucumber corpus to validate the fix. This directly addresses the 11/34 problem with no architectural changes.

## 2. Technique Catalog

### 2A. LABELING — Document-Context Propagation

---

#### Technique A: file_labels Merge (Quick Win)

**How it works:** During dataprep ingestion, after per-chunk labeling completes, merge the document-level `file_labels` (already fetched from document metadata) into every chunk's label set. This is a pure post-processing union operation — no additional LLM calls, no pipeline restructuring.

**Mechanism:** For each chunk `c` in document `d`: `chunk_labels[c] = chunk_labels[c] ∪ file_labels[d]`

**Expected quality lift:** Directly solves the observed problem. If the cucumber document's file_labels include "Cucumber" (which they should, since the file is a cucumber cultivation guide), then all 34 chunks will carry the "Cucumber" label after the merge, up from 11/34. The exact coverage improvement depends on how complete and accurate the file_labels are, but the mechanism guarantees that no chunk in a document can lose the document's subject label.

**Cost:** Zero. No additional LLM calls. The merge is an in-memory set union per chunk during the existing ingestion pipeline.

**Complexity:** Trivial. A few lines of Python in `genieai_dataprep_arangodb.py`, within the chunk-labeling post-processing step. No new dependencies, no model changes, no schema migration.

**Fit for 8B remote model + multilingual:** Perfect fit. The technique is model-agnostic and language-agnostic. It operates on label metadata, not on text generation, so model size and language coverage are irrelevant.

**Implementation notes:**
- In `genie-ai-overlay/dataprep/genieai_dataprep_arangodb.py`, after the chunk labeling loop completes, iterate over all chunks and union `file_labels` into each chunk's label array.
- Deduplicate the resulting label set.
- Store the merged labels in the chunk document in ArangoDB (the `labels` field).
- Consider storing a flag (e.g., `label_source: "chunk" | "file" | "merged"`) for debugging and future ablation studies.

**State:** Proven concept (metadata propagation is standard practice in production RAG systems). No published benchmark for this specific pattern because it is considered obvious engineering, not a research contribution.

---

#### Technique B: Two-Pass Labeling (Document-Level then Chunk-Level with Context)

**How it works:** Pass 1 labels the document as a whole (or uses `file_labels`) to derive a set of document-level labels. Pass 2 labels each chunk individually but provides the document-level labels as context in the labeling prompt, instructing the LLM to consider both the chunk content and the document's known subject.

**Mechanism:**
- Pass 1: `doc_labels = LLM(document_summary_or_full_text, taxonomy)` — one call per document.
- Pass 2: For each chunk: `chunk_labels = LLM(chunk_text + doc_labels_as_context, taxonomy)` — same number of calls as current pipeline, but the prompt includes the document's subject context.

**Expected quality lift:** Should improve over Technique A because the LLM can make informed per-chunk decisions (e.g., a chunk about "irrigation scheduling" in a cucumber document might get both "Cucumber" and "Irrigation" rather than just the inherited "Cucumber"). However, the incremental gain over Technique A is uncertain — if the LLM in pass 2 simply re-confirms the file_labels that were merged in Technique A, the benefit is marginal.

**Cost:** One additional LLM call per document (pass 1). For a typical document, this is negligible (one call vs. ~1700 chunk calls in the cucumber case). Pass 2 has identical cost to the current pipeline. Total overhead: <0.1% increase in LLM calls.

**Complexity:** Moderate. Requires:
1. A document-level labeling prompt and call (can reuse the existing label taxonomy and `response_format` JSON mode).
2. Modifying the chunk-level labeling prompt template to include a `{document_labels}` placeholder.
3. Handling the case where pass 1 fails or returns no labels (fallback to current behavior).

**Fit for 8B remote model + multilingual:** Good fit. The document-level call uses the same model and JSON mode already validated on granite-4.1-8b. The augmented chunk prompt adds ~50-100 tokens of context (the document labels), which is well within the model's capacity. Multilingual compatibility depends on the model's ability to handle the augmented prompt in Spanish — this is likely fine given that the current Spanish labeling already works, but should be tested.

**Caveat:** Anthropic explicitly tested prepending generic document summaries to chunks before retrieval and found "very limited gains" compared to per-chunk context. While their test was about retrieval embeddings (not labeling), the analogous concern applies: a static document-level context prepended to every chunk may add noise without improving the labeling decision for chunks that are already well-labeled. The value is specifically for chunks where the document subject is missing.

**Implementation notes:**
- Pass 1 can use `file_labels` directly if they exist (skipping the LLM call), making this a superset of Technique A.
- The pass-2 prompt modification: add a line like "This chunk is from a document about: {doc_labels}. Consider whether these topics apply to this chunk." before the existing labeling instructions.
- Batch the pass-2 calls exactly as currently done (8 chunks/call, concurrency 20).

**State:** Not formally benchmarked. The two-pass pattern is used in some production systems (document-then-chunk classification), but no peer-reviewed study isolates its effect on retrieval quality through labeling.

#### Technique C: Contextual/Doc-Summary Labeling (Anthropic-Inspired)

**How it works:** Inspired by Anthropic's Contextual Retrieval. For each chunk, prepend a short document-level context (title, subject, or 1-2 sentence summary) to the chunk text before labeling. The LLM sees both the chunk and the document context, enabling it to infer the document's subject for chunks that don't mention it.

**Critical distinction from Anthropic's Contextual Retrieval:** Anthropic's method generates a *separate, chunk-specific* context via a per-chunk LLM call that reads the whole document plus that individual chunk. That per-chunk contextualization is what achieves their measured gains. A *static* document summary prepended identically to every chunk is the cheaper variant that Anthropic explicitly tested and found to have "very limited gains" for retrieval embeddings.

For labeling (not embedding), a static document summary may still help because the task is simpler (assign taxonomy labels, not generate retrieval-relevant context). But the evidence from Anthropic's retrieval experiments cautions against expecting large gains from the static approach.

**Mechanism:** For each chunk `c` in document `d`:
```
input_text = f"Document: {doc_title}\nSubject: {doc_subject}\n\nChunk:\n{chunk_text}"
labels = LLM(input_text, taxonomy)
```

**Expected quality lift:** Uncertain. Likely improves over current per-chunk labeling for chunks missing the document subject, but the incremental gain over Technique A (file_labels merge) is unclear. If the file_labels already contain the document subject, the LLM sees the same information whether it's in the prompt context (Technique C) or merged post-hoc (Technique A) — the difference is whether the LLM *uses* the context to assign additional labels beyond what file_labels provides.

**Cost:** No additional LLM calls (same number of calls as current pipeline). Each call's prompt is ~50-100 tokens longer (the document context header), marginally increasing token usage per call but not call count.

**Complexity:** Low-moderate. Modify the chunk labeling prompt template to include a document-context header. Requires having a document title/summary available (can use the filename or a simple metadata field).

**Fit for 8B remote model + multilingual:** Reasonable. The augmented prompt is short and within the model's capacity. The document title/summary is typically available in the same language as the document (Spanish for el-salvador deployment), so cross-lingual issues are minimal.

**State:** The static-summary variant is explicitly dismissed by Anthropic for retrieval ("very limited gains"). For labeling specifically, no peer-reviewed evidence exists. The per-chunk variant (Anthropic's actual Contextual Retrieval) is proven for retrieval but requires per-chunk LLM calls — see Section 3.

#### Technique D: Embedding-Based Label Classification (Zero LLM at Index Time)

**How it works:** Instead of using an LLM to assign labels per chunk, compute the similarity between each chunk's embedding and each label's embedding (or label description embedding). Assign labels where similarity exceeds a threshold. This is the `LABELING_STRATEGY=embedding` approach already under development at GENIE.AI.

**Mechanism:**
- Pre-compute label embeddings from label names/descriptions (once, at startup).
- For each chunk: compute chunk embedding (already done for vector storage).
- Compute cosine similarity between chunk embedding and each label embedding.
- Assign labels where similarity > threshold (configurable).

**Expected quality lift:** Directly addresses the document-context problem IF label descriptions include the document subject. For example, if the "Cucumber" label's embedding is computed from a description like "Cucumber cultivation, growing, harvesting, pest management for cucumbers," then a chunk about "pest control" that mentions cucumber-specific pests will have high similarity to the "Cucumber" label even if the chunk doesn't explicitly say "cucumber." However, a chunk about generic "planning" in a cucumber document may still have low similarity to the "Cucumber" label — the embedding approach doesn't inherently know the document context.

**Cost:** Zero additional LLM calls. Label embeddings are computed once. Chunk embeddings are already computed for vector storage. The similarity computation is a matrix multiply (cheap).

**Complexity:** Moderate. Requires:
1. Defining label descriptions (not just label names) for each taxonomy category.
2. Computing and caching label embeddings.
3. Tuning the similarity threshold per label or globally.
4. Handling multi-label assignment (top-K labels above threshold, or all labels above threshold).

**Fit for 8B remote model + multilingual:** Good fit for the embedding computation (uses TEI, already deployed). The quality depends heavily on the quality of label descriptions and the multilingual capability of the embedding model. Spanish label descriptions must be semantically meaningful in the embedding space — this requires testing with the actual embedding model (not just English jina models).

**Important limitation:** Embedding-based labeling does NOT inherently propagate document context. A chunk about "irrigation planning" in a cucumber document will have similar embeddings whether the document is about cucumbers or tomatoes. To solve the document-context problem, this technique should be combined with Technique A (file_labels merge) — the embedding labels provide chunk-specific labels, and the file_labels merge ensures document-level coverage.

**State:** Conceptual (embedding-based classification is well-established in NLP), but the specific application to RAG taxonomy labeling is not formally benchmarked in the literature. GENIE.AI's own development of this approach is the primary evidence.

### 2B. RETRIEVAL — Document-Context-Aware Techniques

---

#### Contextual Retrieval (Anthropic)

**How it works:** For each chunk, an LLM generates a 50-100 token natural-language context that situates the chunk within its source document. This context is prepended to the chunk before embedding and (optionally) before BM25 indexing. The LLM prompt provides the entire document plus the individual chunk and asks for a succinct contextualization.

**Quality lift (verified findings):**
- Anthropic's evaluation: top-20-chunk retrieval failure rate reduced by 35% (contextual embeddings alone), 49% (contextual embeddings + contextual BM25), 67% (with reranker). Baseline failure rate was 5.7% on 200k-token synthetic documents.
- Independent benchmark (arXiv:2604.01733v1) on financial text-and-table documents: only +2.8pp Recall@5 for dense (R@5: 0.587 → 0.615) and +2.2pp for hybrid (R@5: 0.695 → 0.717). NOT reproducing the headline 49% figure. The paper ranks contextual retrieval as "consistent moderate gains at one-time cost," third priority behind hybrid fusion and reranking.

**Cost:** One LLM call per chunk at indexing time. For GENIE.AI's cucumber document (34 chunks), this is 34 additional LLM calls using the remote 8B model. At the achieved throughput (batching 8 chunks/call, concurrency 20), this adds ~4-5 calls' worth of time (34 chunks / 8 per batch = ~5 batches). The cost is proportional to document length.

**Critical cost caveat:** Anthropic's cost analysis ($1.02/M tokens) relies on prompt caching with a 61-90% cache hit rate on their hosted Claude API. For GENIE.AI's self-hosted vLLM, vLLM's Automatic Prefix Caching (APC) provides the equivalent economic benefit — repeated system-prompt prefixes reuse cached KV blocks, reducing GPU compute time. There is no per-token billing on self-hosted infrastructure; cost is GPU-hours, which APC reduces proportionally. However, the quality of the 50-100 token context generated by an 8B model (granite-4.1-8b) is unvalidated — Anthropic used Claude, a frontier model. An 8B model may generate lower-quality contextualization, reducing the technique's effectiveness.

**Complexity:** Moderate-high. Requires:
1. A context-generation prompt template.
2. An LLM call per chunk (can batch, but each chunk needs document-level context in the prompt — the document prefix is the same, the chunk suffix differs).
3. Modifying the embedding pipeline to prepend generated context before embedding.
4. Storing the contextualized chunk text (or storing context separately and prepending at query time).

**Fit for GENIE.AI:** Constrained. The per-chunk LLM call at indexing time is the cost profile GENIE.AI moved away from (the labeling optimization from 35min to 0.9min was specifically about reducing LLM calls). Adding contextual retrieval would roughly double the LLM call count at indexing (one call for labeling + one call for context generation per chunk). The self-hosted 8B model may not produce context quality comparable to Claude. The technique is most valuable for corpora with severe context-loss problems (long documents with many context-dependent chunks); GENIE.AI's service-category documents may be shorter and less context-dependent than Anthropic's 200k-token synthetic test set.

**State:** Proven by Anthropic (engineering blog + cookbook). Independent benchmark shows more modest gains. Production-deployed at scale. Not peer-reviewed.

Sources: [1], [2], [3]

#### Late Chunking (Jina AI)

**How it works:** Instead of chunking the document into small pieces and embedding each independently, the entire document is tokenized and passed through a long-context embedding model in one forward pass. The model processes all tokens with full attention (each token attends to all other tokens in the document). Then, chunk boundaries are applied at the token level: for each chunk, the token embeddings within that chunk's boundaries are mean-pooled to produce a context-aware chunk embedding.

**Mechanism:**
1. Tokenize entire document.
2. Run the transformer on all tokens (full self-attention across the entire document).
3. Define chunk boundaries (same as current chunking).
4. For each chunk: mean-pool the token-level embeddings within that chunk's boundaries.

The key insight: because the transformer's self-attention spans the entire document, each token's embedding already incorporates context from all other tokens in the document. A chunk about "irrigation" in a cucumber document will have embeddings influenced by the word "cucumber" elsewhere in the document, even if the chunk itself doesn't mention cucumber.

**Quality lift (verified findings):**
- 2.70-3.63% relative nDCG@10 improvement over naive chunking (1.5-1.9% absolute), averaged across three models and four BeIR datasets.
- Largest gains at small chunk sizes and on datasets where cross-chunk context is meaningful.
- On needle-in-haystack tasks: "not useful, as the additional context from the document is totally irrelevant."
- Financial-document query cosine similarity: late chunking 0.8516 vs contextual embedding 0.8590 vs naive 0.6343 — comparable to Anthropic's LLM-based Contextual Retrieval at zero LLM cost.

**Cost:** Zero LLM calls. The only cost is running the embedding model on the full document (one forward pass on the entire document instead of N forward passes on N chunks). For a long-context embedding model, this may actually be cheaper than naive chunking (one large batch vs. many small batches).

**Critical constraint (verified finding):** Late chunking requires a long-context embedding model (>=8192-token context window, e.g., jina-embeddings-v2-base-en). It is NOT applicable to short-context models (512 tokens). GENIE.AI's TEI embedding model would need to support >=8192-token context for this technique to work. This is a model-swap constraint — the technique is a pure architectural change with no model training required, but it requires the right model.

**Critical constraint (verified finding):** All evaluations are English-only (jina-embeddings-v2-base-en, English Wikipedia passages, MTEB English tasks SciFact/TRECCOVID). No Spanish or cross-lingual evaluation exists. Spanish effectiveness is unvalidated — a material risk for GENIE.AI's Spanish-language government documents.

**Complexity:** Moderate. Requires:
1. Switching to a long-context embedding model (if TEI's current model is short-context).
2. Implementing the token-level chunking and pooling logic (the Jina late-chunking library provides reference implementations).
3. Modifying the dataprep pipeline to embed full documents rather than individual chunks.

**Fit for GENIE.AI:** Promising but blocked by the embedding model constraint. If GENIE.AI's TEI uses a model with >=8192 context (e.g., bge-m3 supports 8192), late chunking is feasible. The zero-LLM-cost profile is ideal for the cost-sensitive deployment. The English-only evaluation is a risk that must be mitigated by testing on Spanish documents before adoption. The modest quality gains (2-4% relative) are smaller than what file_labels merge could deliver for the specific labeling problem.

**State:** Published peer-reviewed paper (arXiv:2409.04701). Open-source implementation available. English-only evaluation. Not widely deployed in production RAG systems yet — still primarily a research contribution from Jina AI.

Sources: [4], [5], [6]

#### RAPTOR (Recursive Abstractive Tree Retrieval)

**How it works:** RAPTOR constructs a multi-level tree structure over a document. At the base level, chunks are embedded and clustered (GMM on UMAP-reduced embeddings). Each cluster is summarized by an LLM, creating a higher-level node. This clustering-and-summarization recurses, building a tree where each level represents progressively more abstract summaries of the document. Retrieval can then access both fine-grained chunks and coarse-grained summaries, enabling multi-hop reasoning.

**Quality lift (verified finding):** 82.6% accuracy on QuALITY multi-hop QA (vs 62.3% previous best). However, this is on a multi-hop QA benchmark, not standard retrieval. The technique's advantage is specifically for questions that require synthesizing information across multiple parts of a document — not for single-chunk retrieval.

**Cost:** One LLM summarization call per cluster per tree level. For a 34-chunk document with, say, 5 clusters at level 1, 2 clusters at level 2: ~7 LLM calls. For GENIE.AI's ~1700-chunk corpus (multiple documents), this scales to tens of LLM calls per document. The remote 8B model would be used for summarization.

**Critical limitation (verified finding):** RAPTOR does NOT propagate document-level labels to chunks. Clustering is purely embedding-similarity-based. It addresses a different problem (multi-hop QA) than GENIE.AI's labeling gap.

**Complexity:** High. Requires:
1. Embedding-based clustering (GMM + UMAP).
2. LLM summarization per cluster.
3. Tree construction and storage.
4. Modified retrieval to traverse the tree.
5. Storing the tree structure in ArangoDB (graph database is well-suited for this).

**Fit for GENIE.AI:** Poor fit for the current problem. RAPTOR solves multi-hop reasoning, not document-context labeling. The cost (tens of LLM calls per document) and complexity (tree construction, clustering, modified retrieval) are disproportionate to the labeling gap. However, ArangoDB's graph capabilities would naturally support the tree structure if RAPTOR were adopted for other reasons (e.g., complex multi-hop government service questions). The models are pluggable (verified finding: RAPTOR supports custom models including local LLMs via CustomSummarizationModel, CustomQAModel, CustomEmbeddingModel).

**State:** Published peer-reviewed paper (arXiv:2401.18059). Open-source implementation. Academic evaluation only (QuALITY benchmark). Not widely deployed in production.

Sources: [7], [8]

#### Hierarchical / Parent-Child (Small-to-Big) Retrieval

**How it works:** Documents are chunked at two levels: large "parent" chunks (e.g., 1024 tokens) and smaller "child" chunks (e.g., 128, 256, 512 tokens) that reference their parent via an ID pointer. At indexing time, only the smaller child chunks are embedded and indexed (higher retrieval precision). At retrieval time, when a child chunk matches, the parent chunk is returned to the LLM instead (more context for generation).

**Quality lift:** No published benchmark isolating the parent-child pattern's effect on retrieval quality. The technique is primarily a generation-quality improvement (more context to the LLM) rather than a retrieval-precision improvement.

**Cost (verified finding):** Zero LLM cost at indexing time. It only changes chunk organization and retrieval — no LLM calls. The embedding cost may increase slightly (more child chunks to embed), but each child is smaller.

**Complexity:** Moderate. Requires:
1. Two-level chunking (parent + child).
2. ID linking between child and parent chunks.
3. Modified retrieval to return the parent chunk on a child hit.
4. Storing both levels in ArangoDB (parent-child edge or metadata reference — graph database is ideal for this).

**Fit for GENIE.AI:** Moderate fit. The zero-LLM-cost profile is attractive. ArangoDB's graph structure naturally supports parent-child relationships via edges. However, this technique does not directly solve the labeling problem — it improves generation context, not label coverage. It could complement Technique A (file_labels merge): the merge fixes the labeling gap, and parent-child retrieval improves the context available to the LLM at generation time.

**State:** Widely deployed in production RAG systems (LlamaIndex provides built-in SentenceWindowNodeParser and RecursiveRetriever primitives). Proven-in-production. Not formally benchmarked in isolation.

Sources: [9]

#### Document-Summary Indexing / Multi-Vector Retrieval

**How it works:** For each document, generate a summary (or use the document title/abstract). Index the summary separately as a "document-level" retrievable unit. At query time, retrieve both chunk-level matches and document-summary matches, then use the document-summary matches to promote or filter chunks from matching documents.

**Quality lift:** Anthropic explicitly evaluated "summary-based indexing" and found "low performance." The document summary is too coarse to identify specific relevant chunks — it helps find the right document but not the right passage within it.

**Cost:** One LLM summarization call per document (or zero if using existing metadata like title/abstract). Low cost.

**Complexity:** Low-moderate. Requires:
1. Document summary generation (or reuse existing metadata).
2. Additional ArangoDB collection or index for document summaries.
3. Modified retrieval to incorporate document-level matches.

**Fit for GENIE.AI:** Low priority. Anthropic's evaluation found this approach underperforms. However, the concept of a document-level retrievable unit could be useful as a first-stage filter: retrieve matching documents first (using document summaries + labels), then retrieve chunks within those documents. This "retrieve-then-filter" pattern is essentially what GENIE.AI's label filtering already does — the document-summary indexing would add a semantic (rather than label-based) document filter.

**State:** Evaluated and dismissed by Anthropic for retrieval quality. Concept used in some production systems as a coarse pre-filter. Not recommended as a primary technique.

Sources: [1]

#### ColBERT / Late-Interaction Retrieval

**How it works:** Instead of producing a single embedding vector per chunk (dense retrieval), ColBERT produces token-level embeddings for both the query and the document. At query time, the score is computed as the max-similarity sum across all query-token to document-token pairs (late interaction). This preserves fine-grained token-level matching while still enabling pre-computed document-side embeddings.

**Quality lift:** ColBERTv2 achieves MRR@10=0.397 on MS MARCO dev, a standard IR benchmark. Jina-ColBERT-v2 extends this to multilingual settings (XLM-RoBERTa backbone, trained on 29 languages).

**Critical caveats (verified finding on Jina-ColBERT-v2):** The claim that Jina-ColBERT-v2 "outperforms English-only ColBERTv2 on MIRACL multilingual benchmarks" is unsupported — ColBERTv2 is monolingual and cannot perform multilingual retrieval, so the comparison is trivially true and not a competitive finding. On MIRACL aggregate, Jina-ColBERT-v2 (62.3 nDCG) actually underperforms mDPR-FT (62.7). The compression statistics (768→128 dims, 1.59% nDCG@10 drop) were misattributed in the research — the 1.59% applies to a further 128→64 reduction via Matryoshka Representation Loss, not to the standard ColBERT projection.

**Cost:** No LLM calls at indexing. However, multi-vector storage is significantly more expensive: each chunk stores N token-level vectors (typically 128-dim per token, hundreds of tokens per chunk) rather than a single vector. Storage and retrieval compute scale with token count.

**Complexity:** High. Requires:
1. Switching the embedding model to a ColBERT-family model.
2. Multi-vector storage in ArangoDB (ArangoDB's vector index is designed for single-vector-per-document; multi-vector requires custom indexing or a separate store).
3. Modified retrieval to perform late-interaction scoring (not standard vector search).
4. TEI may not support ColBERT-style multi-vector output.

**Fit for GENIE.AI:** Poor fit for the current problem. ColBERT addresses token-level matching precision, not document-context propagation. The multi-vector storage requirement is incompatible with ArangoDB's single-vector index design without significant custom engineering. The multilingual ColBERT evidence is weaker than initially claimed. The complexity is disproportionate to the labeling gap.

**State:** ColBERTv2 is published (NAACL 2022) and used in some production systems. Jina-ColBERT-v2 is published (MRL Workshop 2024) but with the caveats noted above. Multi-vector retrieval is an active research area but not standard in production RAG.

Sources: [10], [11]

#### Graph-Based Retrieval (Leveraging ArangoDB)

**How it works:** GENIE.AI already uses ArangoDB as a graph + vector multi-model database. The graph structure can encode document-level relationships: document → chunk edges, document → label edges, chunk → label edges, and document → document similarity edges. At retrieval time, graph traversal can propagate document-level context to chunks: when a document matches a query (via document-level labels or metadata), all chunks connected to that document via edges can be included or promoted in the retrieval results.

**Quality lift:** No published benchmark for this specific pattern (graph-based document-context propagation in a RAG pipeline). The quality lift depends entirely on the graph schema design and traversal logic. However, the concept is sound: graph traversal provides O(1) access to all chunks in a document, enabling instant document-context-aware retrieval without any LLM calls.

**Cost:** Zero LLM calls. Graph traversal is a database query (AQL in ArangoDB). The cost is query latency, which is typically sub-millisecond for simple traversals.

**Complexity:** Moderate. Requires:
1. Defining a graph schema for document-chunk-label relationships (may already partially exist).
2. Writing AQL traversal queries for document-context-aware retrieval.
3. Modifying the retriever to use graph traversal alongside vector search.

**Fit for GENIE.AI:** Strong fit. ArangoDB is already the store, and its graph capabilities are a core architectural advantage. This approach is the natural way to leverage the existing infrastructure for document-context-aware retrieval. Combined with Technique A (file_labels merge), graph-based retrieval can provide a two-tier retrieval: (1) vector search for chunk-level relevance, (2) graph traversal for document-context promotion (ensure all chunks from a matching document are considered).

**Specific implementation idea:** When a user queries for "cucumber pests," the retriever performs vector search and finds relevant chunks. Simultaneously, a graph query identifies documents labeled "Cucumber" and promotes their chunks in the result set. This is essentially a graph-enhanced version of the label filtering that GENIE.AI already does, but with document-level awareness.

**State:** GENIE.AI already uses hybrid vector-graph retrieval. The specific enhancement of using graph traversal for document-context propagation is an engineering extension of the existing architecture, not a new research technique. Graph-based RAG is an active research area (e.g., GraphRAG, Microsoft 2024), but GENIE.AI's use case is simpler — leveraging existing graph edges for document-level context, not building a knowledge graph from scratch.

## 3. Honest Evaluation of Contextual Retrieval

### The Headline Numbers

Anthropic's Contextual Retrieval blog reports a 49% reduction in top-20 retrieval failure rate (5.7% → 2.9%) when combining contextual embeddings with contextual BM25, rising to 67% (5.7% → 1.9%) with a reranker. These are impressive numbers, measured on 200k-token synthetic documents designed to stress-test context-loss scenarios.

However, the independent benchmark (arXiv:2604.01733v1) on financial text-and-table documents found only +2.8pp Recall@5 for dense retrieval (0.587 → 0.615) and +2.2pp for hybrid (0.695 → 0.717) — a modest, not dramatic, improvement. The paper ranks contextual retrieval third in priority behind hybrid fusion and reranking, characterizing it as "consistent moderate gains at one-time cost."

The discrepancy likely reflects domain and document characteristics: Anthropic's synthetic documents are specifically designed to maximize context-loss (200k tokens, many cross-references), while the financial benchmark uses real-world documents where context loss may be less severe. GENIE.AI's service-category documents are likely closer to the financial benchmark's profile (structured, domain-specific, moderate length) than to Anthropic's stress-test scenario.

### The Cost Problem

Contextual Retrieval requires one LLM call per chunk at indexing time. For GENIE.AI:
- The cucumber document (34 chunks) would need 34 additional LLM calls for context generation.
- At the current pipeline's throughput (batching, concurrency 20), this adds modest wall-clock time.
- On a remote 8B model (granite-4.1-8b), the quality of the generated context is unvalidated. Anthropic used Claude, a frontier model — an 8B model may produce shorter, less informative, or less accurate contextualization.

vLLM's Automatic Prefix Caching (APC) mitigates the cost: the shared system prompt + document context is a repeated prefix across all per-chunk calls, so APC reuses the cached KV blocks. On self-hosted infrastructure, there is no per-token billing — cost is GPU-hours, which APC reduces. But the calls still consume GPU time that could be used for other workloads.

### Does Doc-Summary Labeling (Technique C) Capture Most of the Gain More Cheaply?

**Partially, but with important caveats:**

1. **For the labeling problem (GENIE.AI's actual issue):** Technique A (file_labels merge) is strictly better than Contextual Retrieval for the labeling gap. It is zero-cost, deterministic, and guarantees coverage. Contextual Retrieval addresses a different problem (embedding-level context loss), not label-level context loss.

2. **For the embedding problem (if GENIE.AI also has context-loss in vector retrieval):** The evidence is mixed. Anthropic found that static document summaries prepended to chunks yield "very limited gains" for retrieval — the per-chunk contextualization is what drives the improvement. However, the independent benchmark's modest gains suggest that even per-chunk contextualization provides only incremental improvement on domain-specific corpora.

3. **The honest assessment:** Contextual Retrieval is a proven technique that provides real, measurable improvements for corpora with severe context-loss problems. GENIE.AI's labeling gap is NOT primarily a context-loss problem in the embedding sense — it is a label-coverage problem. The techniques that directly address label coverage (Technique A: file_labels merge, Technique D: embedding-based labeling) are cheaper, simpler, and more targeted.

**Recommendation:** Do not adopt Contextual Retrieval as the primary solution to the labeling gap. File the technique as a future enhancement for embedding quality (Phase 3), to be evaluated after the labeling gap is closed and if retrieval quality metrics indicate context-loss in the embedding space.

## 4. Ranked Recommendations for GENIE.AI

### Phase 1: Quick Wins (Days, Zero LLM Cost)

#### Recommendation 1: Implement file_labels Merge (Technique A)

**Priority:** Critical. This directly solves the 11/34 problem.

**Effort:** <1 day.

**Implementation:**
- File: `genie-ai-overlay/dataprep/genieai_dataprep_arangodb.py`
- After the chunk labeling loop, before writing chunks to ArangoDB:
  1. Fetch `file_labels` (already available in the pipeline).
  2. For each chunk: `chunk['labels'] = list(set(chunk['labels'] + file_labels))`
  3. Store merged labels in the chunk document.
- Add a `label_source` field for debugging: `"merged"` if file_labels were added, `"chunk"` if only chunk-level labels.

**Validation:** Re-ingest the cucumber document and verify all 34 chunks carry the "Cucumber" label. Compare retrieval results for "cucumber" queries before and after.

**Risk:** None. The merge is additive (never removes labels) and deterministic.

---

#### Recommendation 2: Validate Embedding-Based Labeling (Technique D) with file_labels Fallback

**Priority:** High. Reduces labeling cost further while maintaining quality.

**Effort:** 2-3 days (if not already in development).

**Implementation:**
- Compute label embeddings from label descriptions (not just label names — descriptions provide richer semantic signal).
- For each chunk: compute cosine similarity to each label embedding, assign labels above threshold.
- Always merge file_labels as a fallback (combines Techniques A + D).
- Tune threshold on the cucumber corpus: compare embedding-assigned labels to LLM-assigned labels.

**Risk:** Threshold tuning is corpus-dependent. Spanish label descriptions must be semantically meaningful in the embedding model's space — test with the actual TEI model, not English-only models.

---

### Phase 2: Medium Efforts (Weeks, Low-Moderate Cost)

#### Recommendation 3: Graph-Enhanced Document-Context Retrieval

**Priority:** Medium. Leverages ArangoDB's graph capabilities for document-context-aware retrieval.

**Effort:** 1-2 weeks.

**Implementation:**
- Ensure document → chunk edges exist in ArangoDB (may already be present).
- Add a document-level retrieval path in `genie-ai-overlay/retriever/genieai_retriever_arangodb.py`:
  1. Standard vector search for chunk-level relevance (existing).
  2. Graph query: for each retrieved chunk, fetch all sibling chunks in the same document.
  3. Promote sibling chunks that share labels with the query's requested labels.
- This ensures that if ANY chunk from a cucumber document is retrieved, the retriever can promote other labeled chunks from the same document.

**Risk:** Increased retrieval latency from graph traversal. Mitigated by ArangoDB's sub-millisecond traversal for shallow queries. Test latency impact on the deployment.

---

#### Recommendation 4: Parent-Child Chunking for Generation Context

**Priority:** Low-medium. Improves generation quality (more context to the LLM) but does not solve the labeling gap.

**Effort:** 1 week.

**Implementation:**
- In dataprep: create parent chunks (1024 tokens) and child chunks (256 tokens) with ID links.
- Index child chunks for retrieval (higher precision).
- At retrieval: on a child hit, return the parent chunk to the LLM (more context).
- Store parent-child edges in ArangoDB (graph database is ideal for this).

**Risk:** Storage increase (more chunks to index). Retrieval logic change. Should be evaluated against current chunking to ensure no regression.

---

### Phase 3: Larger Efforts (Months, Justified by Metrics)

#### Recommendation 5: Late Chunking (If Embedding Model Supports It)

**Priority:** Low. Only if retrieval quality metrics show embedding-level context loss AND the TEI embedding model supports >=8192-token context.

**Effort:** 2-4 weeks.

**Prerequisites:**
1. Verify TEI's current embedding model context window. If <8192, evaluate switching to a long-context multilingual model (e.g., bge-m3, which supports 8192 tokens and has multilingual support).
2. Validate late chunking on Spanish documents (no published Spanish evaluation — GENIE.AI must generate its own evidence).

**Implementation:**
- Replace naive chunk-then-embed with embed-whole-document-then-pool-per-boundary.
- Use the Jina late-chunking reference implementation as a guide.
- Benchmark: compare retrieval quality (Recall@k, MRR@k) on GENIE.AI's corpus before and after.

**Risk:** English-only published evaluation. Modest published gains (2-4% relative). Model swap may affect other parts of the pipeline. Only justified if Phase 1-2 improvements are insufficient and metrics show embedding-level context loss.

---

#### Recommendation 6: Contextual Retrieval (If Phase 1-3 Are Insufficient)

**Priority:** Lowest. Only if all other techniques are implemented and retrieval quality still shows context-loss gaps.

**Effort:** 2-4 weeks.

**Prerequisites:**
1. Quantitative evidence that chunks are being missed due to embedding-level context loss (not label coverage, which Phase 1 addresses).
2. Validation that the 8B model can generate useful per-chunk context (run a pilot on 10-20 chunks, evaluate context quality manually).

**Implementation:**
- Add a context-generation pass in dataprep: for each chunk, call the remote vLLM with the full document + chunk, generate 50-100 token context.
- Prepend generated context to chunk text before embedding.
- Enable vLLM APC (`--enable-prefix-caching`) to reduce GPU time for the shared document prefix across per-chunk calls.
- Benchmark: compare retrieval quality with and without contextual embeddings.

**Risk:** Per-chunk LLM call cost (the profile GENIE.AI moved away from). 8B model context quality unvalidated. Modest published gains on domain-specific corpora (+2.8pp). Only justified if the labeling gap is closed and metrics still show retrieval deficits.

## 6. Cautions on Refuted Claims

The following claims were investigated and **refuted** during adversarial verification. They should NOT be relied upon for GENIE.AI decision-making:

1. **"Reranking is the single most impactful retrieval improvement, beating contextual retrieval."** This is true only for a specific financial text-and-table benchmark using Cohere's hosted cross-encoder reranker (arXiv:2604.01733v1). Anthropic's own data shows contextual retrieval contributing MORE to failure reduction (49pp) than the reranker (18pp marginal). GENIE.AI already has a reranker (TEI-based). The relative ranking of techniques is domain-dependent and unmeasured for GENIE.AI's multilingual public-sector corpus.

2. **"Convex Combination fusion (alpha=0.5) outperforms RRF and is directly testable on GENIE.AI."** GENIE.AI does NOT use Reciprocal Rank Fusion — its retriever uses ArangoDB's native view-based hybrid search. There is no RRF parameter to swap. The fusion finding is specific to financial-table retrieval and does not transfer.

3. **"Reranker candidate depth has a critical threshold of 50 candidates."** This threshold is specific to financial text-and-table retrieval with a Cohere reranker. GENIE.AI uses a TEI-based reranker with `RERANKER_TOP_N=2`. The appropriate top-k must be empirically tuned on GENIE.AI's own corpus, not imported from a financial benchmark.

4. **"Contextual Retrieval's improvement mechanism is metadata enrichment, directly analogous to GENIE.AI's label propagation."** Contextual Retrieval uses LLM-generated natural-language prose summaries, NOT structured metadata. GENIE.AI's label propagation is structurally distinct (deterministic categorical tags vs. generative free-text summaries). The two are only loosely analogous.

5. **"Prompt caching is proprietary to Anthropic and unavailable to self-hosted vLLM."** False. vLLM provides Automatic Prefix Caching (--enable-prefix-caching), which delivers the same economic benefit (skipped recomputation of cached prefix KV blocks). OpenAI also offers automatic prompt caching (up to 90% off cached input). Self-hosted cost is GPU-hours, which prefix caching reduces proportionally.

6. **"Overlapping chunk boundaries are not needed when using late chunking."** GENIE.AI uses standard naive chunking (RecursiveCharacterTextSplitter), not late chunking. For naive chunking, overlap provides modest improvements in 3 of 4 tested datasets. The late-chunking overlap finding does not apply to GENIE.AI's current pipeline.

7. **"Jina-ColBERT-v2 outperforms ColBERTv2 on MIRACL multilingual benchmarks with minimal compression loss."** The comparison is trivially true (ColBERTv2 is monolingual). On MIRACL aggregate, Jina-ColBERT-v2 underperforms mDPR-FT. The compression statistics were misattributed in the source research.
