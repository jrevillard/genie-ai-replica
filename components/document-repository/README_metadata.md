# Metadata Strategy

## Two-Tier Metadata Extraction

Separate metadata into **two categories** with different extraction stages:

### Basic Metadata (at upload time in Document Repo)

Extracted *immediately after upload* and stored **in the document repository service**, to support browsing/searching even before ingest.

* `file_id` (unique identifier)
* `file_name` 🔍 ✍️ (e.g. `abc123.pdf`. If the file is a webpage, the user can edit to use the content title as the name.)
* `file_size`
* `file_type` 🔍 (MIME type)
* `storage_path` (local relevant path, e.g. `/uploads/abc123.pdf`)
* `labels` 🔍 ✍️ (editable)
* `author` 🔍 ✍️
* `upload_date` 🔍 (timestamp of uploading to the document repository)
* `create_date` 🔍 ✍️ (if extractable from file or user-provided. For example, a PDF created at 2023-10-01T12:00:00Z; a html webpage published at 2023-10-01T12:00:00Z)
* `crawl_date` ✍️ (if applicable, when the file was crawled)
* `source_url` ✍️ (only if the file is a webpage, e.g. `https://example.com/page`)

Use this metadata for:

* User search
* Display in UI

🔍 means the user can search by this metadata field;
✍️ means the user can edit this metadata field.

### Extended Metadata (at ingest time in Dataprep)

Extracted only **after ingestion**, using text processing, embedding, or semantic enrichment inside `dataprep-microservice`.

* `file_id` (shared with Document Repo)
* `language` (detected)
* `chunk_count` (number of text chunks)
* `labels` (Inherited from Document Repo. If not set, auto-generated by LLM)

✅ Use this metadata for:

* RAG input provenance
* KG traceability
* Chunk/embedding management

## Metadata Storage Recommendation

| Component                 | What it stores                    | Where to store                                  |
| ------------------------- | --------------------------------- | ----------------------------------------------- |
| **Document Repository**   | Basic metadata (searchable)       | **Local metadata store** (JSON file or Lite DB) |
| **Dataprep Microservice** | Extended metadata (semantic info) | **ArangoDB (GPU)**                              |

* **Local repo metadata** supports fast lookups and doesn’t need GPU access.
* **Dataprep metadata** is richer, linked to graph nodes/chunks, and needs ArangoDB’s structure.

---

## How to Link the Two?

Use a shared unique `fileId` as the linking key between metadata records.

Example:

```json
// In document repo (local)
{
    "file_id": "9527",
    "file_name": "TBHDQX.pdf",
    "file_size": "1.2MB",
    "file_type": "application/pdf",
    "storage_path": "/uploads/TBHDQX.pdf",
    "labels": ["Arts & Culture", "K-12 Education"],
    "author": "Stephen Chow",
    "upload_date": "2025-05-11T10:30:00Z",
    "create_date": "1993-07-01T12:00:00Z",
    "crawl_date": "",
    "source_url": ""
}
```

```json
// In dataprep (ArangoDB)
{
    "file_id": "9527",
    "language": "zh",
    "chunk_count": 10,
    "labels": ["Arts & Culture", "K-12 Education"]
}
```

## 💐 Bonus: Metadata Lifecycle

| Step     | Action                                    | Metadata Handling                           |
| -------- | ----------------------------------------- | ------------------------------------------- |
| Upload   | Save the file and basic metadata (in JSON)| Local disk (Document Repo)                  |
| Ingest   | Send file + metadata to dataprep          | Extended metadata saved in ArangoDB         |
| Edit     | User edits tags, authors, etc.            | Update local metadata store                 |
| Search   | Search by local metadata (in repo)        | JSON-based index or small DB (e.g. LokiJS)  |
| Trace KG | Show file source in output (from Arango)  | Use `file_id` to trace to document repo path |

## 🏷️ Bonus: Label Logic

| Action                        | Allowed? | Notes                                                                  |
| ----------------------------- | -------- | ---------------------------------------------------------------------- |
| Add/edit label before ingest  | ✅       | Stored locally in document repo metadata                               |
| Auto-generate label on ingest | ✅       | If no label, dataprep generates one via LLM                            |
| Edit label after ingest       | ❌       | Must first **retract** to allow editing                                |
| Retract-ingested file         | ✅       | Removes it from dataprep; re-enables metadata editing in document repo |
| Re-ingest after edit          | ✅       | Sends updated metadata (e.g. label) to dataprep again                  |

### Suggested UI/UX Guidance

> Note on Label Management
> Labels are used to organize and retrieve content within the document repository and downstream dataprep service.
> You may assign or edit labels before ingestion.
> Once a file is ingested into the knowledge base, its metadata becomes immutable for consistency.
> To change a label after ingestion, you must first retract the file, edit the metadata, and then re-ingest it
