## Successes

### 1. createApp() Factory Pattern (Story 2.1)

The foundational investment that enabled the entire epic. Extracting `createApp({ services })` from the 1,251-line `index.js` was the single most important technical decision. It established the Supertest `request(app)` pattern used by all 6 route/service/middleware stories. Without this refactor, no route test could run without starting a real server.

### 2. Centralized Fixture Architecture (Story 2.2)

`createMockUser()`, `createValidToken()`, `createMockReq()`/`createMockRes()`, and the shared-lib mock with all 4 exports. Every subsequent story imported these fixtures. The factory-with-overrides pattern (`{ ...defaults, ...overrides }`) gave each test both consistency and flexibility. The cross-component shapes documented here (users, conversations, files) serve as the contract for Epic 3 (frontend) and Epic 5 (document-repository).

### 3. Progressive Pattern Maturation

Stories 2.3–2.6 followed an increasingly efficient rhythm. Story 2.3 established the route test pattern (mock setup, createApp, Supertest, assertions). Story 2.4 expanded it to 22 routes. Stories 2.5 and 2.6 replicated it for 28 more endpoints. By Story 2.5, the pattern was mechanical — the bottleneck shifted from "how do I test this?" to "what does this route actually do?"

### 4. Review Quality and Consistency

Code reviews systematically strengthened assertions (from `toHaveBeenCalled()` to `toHaveBeenCalledWith()`), added edge case tests (null userId, missing body, empty arrays), and identified security gaps (unauthenticated query access). The review-then-patch cycle was efficient — most stories passed after one round.

### 5. Service Layer Coverage (Story 2.7)

140 tests across 5 services with complex mocking challenges (ArangoDB singletons, Redis caching, ESM dynamic imports, Worker threads). Despite the story being oversized, the coverage is comprehensive: CRUD, error paths, graceful degradation, caching, fallback logic.

### 6. Dev Notes as Survival Guides

Each story's dev notes documented: import-time dependencies, mock setup requirements, route registration patterns, production code issues discovered. These notes are a knowledge base for anyone extending or maintaining these tests.

## Challenges

### 1. Epic Specifications Inaccurate (5/8 stories affected)

The most pervasive challenge. Stories discovered significant gaps between epic definitions and actual codebase:

| Story | Gap Discovered |
|-------|---------------|
| 2.3 | Auth login/refresh endpoints don't exist — only logout |
| 2.4 | Chat routes have 22 endpoints, not 5 (folders, search, stats, query linking) |
| 2.5 | Route path is `/api/service-categories`, not `/api/categories` |
| 2.6 | No file routes exist in gov-chat-backend — files handled by document-repository |
| 2.8 | Rate limiting (express-rate-limit) is a dependency but never used |

**Impact:** Time spent verifying what exists vs. implementing tests. Each story required an exploratory phase before writing any test code.

**Root cause:** Epics were written at an architectural level without validating against the actual codebase.

**Decision:** Pre-verification step required before Epic 3 story creation — verify component structure, API surface, and actual patterns before writing story ACs.

### 2. Story 2.7 Scope Explosion

A single story covering 5 services, 140+ tests, 5 different mock architectures. The review produced 3 decision-needed items and 7 patches. This was 4x larger than a typical story.

**Impact:** Longer review cycles, higher cognitive load, more patches needed.

**Root cause:** Story scope was defined by layer (all services) rather than by complexity or module count.

**Decision:** Adopt a scope rule — max 2 major modules or ~50 initially planned tests per story. Split proactively during story creation.

### 3. Two Error Handling Patterns in Backend

Routes use either `next(error)` (most routes) or direct `res.status(500).json()` (security routes in admin). The global error handler at `index.js:775` has 3 parameters instead of Express's required 4, so Express doesn't recognize it as error middleware. `next(error)` calls bypass the custom JSON handler and get Express's default HTML error.

**Impact:** Test assertions must account for two different error response formats. Story 2.8 couldn't test the actual error handler via `createApp()` and had to use standalone Express apps.

**Root cause:** Pre-existing bug in error handler signature.

**Decision:** Tracked as critical tech debt (TD-B2.1). Fix is simple (add 4th `next` param) but affects production code. Deferred to a separate task, not blocking Epic 3.

### 4. Mock Completeness Discovery Curve

Each story had to discover which mocks were required through trial and error. The shared-lib 4-export requirement, the `{ virtual: true }` flag for Docker-packaged modules, the keycloak service mock chain — these were relearned or re-explained in dev notes across multiple stories.

**Impact:** Initial test runs often crashed with `Cannot destructure property 'X' of undefined` before the correct mocks were in place.

**Mitigation:** Stories 2.1 and 2.2 established the canonical mock patterns. Later stories copied the pattern. But the pattern wasn't formally documented as a standalone guide.

**Decision:** Create a Backend Mock Setup Guide as an action item.

## Key Insights

1. **Test infrastructure stories pay compound dividends.** Stories 2.1 (createApp) and 2.2 (fixtures) were pure infrastructure with no direct FR coverage. But they made every subsequent story faster and more consistent. This pattern should be repeated for every component epic.

2. **Specification accuracy is a pre-requisite, not a nice-to-have.** 5/8 stories discovered significant spec-code mismatches. Pre-verification before story creation is now a process requirement.

3. **Dev notes are force multipliers.** The detailed documentation of mock strategies, bypass patterns, and import chains meant each story built on prior knowledge without re-discovery. This practice must continue.

4. **Review discipline raises the floor systematically.** Consistent focus on stronger assertions, edge cases, and boundary conditions improved quality across all stories. The review-then-patch cycle caught patterns that individual developers missed.

5. **Backend has two error handling conventions.** This split (next(error) vs direct res.status()) is a pre-existing design inconsistency that complicates both testing and error handling. A future refactor should unify this.

6. **Story scope matters for AI-assisted development.** Story 2.7 demonstrated that oversized stories degrade output quality. The 2-module/50-test rule prevents this.
