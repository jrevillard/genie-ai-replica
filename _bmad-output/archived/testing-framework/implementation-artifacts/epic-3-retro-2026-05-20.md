## Successes

### 1. Test Infrastructure Investment (Story 3.1)

Centralized fixtures (`axios.js`, `keycloakAuthService.js`, `store-state.js`, `api-responses.js`) consumed by all 4 subsequent stories. The factory-with-overrides pattern provided consistency and flexibility. Cross-component fixture shapes (user, conversation, file metadata) match backend (Epic 2), satisfying FR36.

### 2. Closure-Based Mock Pattern

Eliminated hoisting issues consistently across all stories. Each story replicated the same skeleton (`jest.mock()` with closure refs, `beforeEach` reset) without re-discovery. The pattern is now validated on both backend (Supertest) and frontend (Vue Test Utils).

### 3. Dev Notes as Survival Guides

Component analyses in Stories 3.2 and 3.3 documented every dependency chain, mock strategy, and technical constraint. ChatBotComponent (2,441 lines) and AdminDashboard (4,429 lines) required detailed mapping of what to mock and why. These notes remain actionable for anyone extending these tests.

### 4. Review Discipline

15 patches applied across 5 stories. Reviews systematically strengthened assertions, added edge cases (null roles in NavBar, double data unwrap in documentFileService), corrected mock data shapes to match real backend responses, and identified missing coverage. Average: 3 patches per story.

### 5. Story 3.5 Mechanical Execution

159 tests across 6 services with a single pattern (httpService mock + endpoint assertions). Despite the volume, zero regressions. The pattern was so well-established by this point that execution was mechanical.

---

## Challenges

### 1. Epic Specs Inaccurate (5/5 stories affected)

Same pattern as Epic 2. Epic referenced non-existent mutations (`ADD_CONVERSATION`, `SET_CURRENT_CONVERSATION`, `ADD_MESSAGE`), wrong service names (`chatService` instead of `chatbotService`), and assumed endpoints that don't exist. Every story required AC remapping to actual code.

### 2. Monolithic Vue Components

ChatBotComponent (2,441 lines, 40+ methods) and AdminDashboard (4,429 lines, 80+ methods) are too large for comprehensive testing. Stories 3.2 and 3.3 had to define strict "what NOT to test" boundaries. Significant portions of these components have no direct test coverage.

### 3. SSE Streaming Coverage Gap

`chatbotService.submitQueryStream()` uses native Fetch API (not axios/httpService). Jest/jsdom mock infrastructure doesn't cover this. The main chat interaction path has no service-level test. Deferred — but it's the core user journey.

### 4. Story 3.5 Scope Explosion (repeat of Epic 2 pattern)

6 services, 159 tests, 9 deferred items. Same issue as Story 2.7 in backend. Pattern is mechanical but volume creates disproportionate review burden. The scope limit agreement from Epic 2 retro was not respected.

### 5. Auth Module Shared State Trap

Auth module exports a shared state object (not a factory function). Story 3.4 had to document the trap and create fresh copies in every test. One missed copy contaminates the entire suite.

### 6. Pre-existing Vue/Test-utils Failures

3 component tests became unstable between stories. Not blocking but indicates fragility in frontend test configuration.

---

## Key Insights

1. **Test infrastructure stories pay compound dividends.** Validated on both backend (Epic 2, Story 2.2) and frontend (Epic 3, Story 3.1). This pattern should be repeated for every component epic.

2. **Epic specs are systematically inaccurate.** 2 out of 2 epics with significant spec-code mismatches. Pre-verification before story creation is now a confirmed necessity, not a nice-to-have.

3. **Monolithic Vue components limit testability.** Components exceeding 2,000 lines cannot be reasonably covered. Observable behavior testing is pragmatic but leaves coverage gaps. This is an architectural concern, not a testing concern.

4. **Team agreements without verification are wishful thinking.** The scope limit rule from Epic 2 was not respected in Epic 3. Agreements need either process enforcement or pragmatic revision.

## Action Items

### Process Improvements

1. **Scope limit — revise to be pragmatic**
   - Owner: Dev (story creator)
   - Rule: HTTP service stories with a mechanical pattern (same mock, same assertion structure) may exceed 50 tests. Stories with >2 modules of divergent behavior MUST be split.
   - Success criteria: No story with >80 tests AND heterogeneous review findings
   - Trigger: All future story creation

2. **Epic spec accuracy — validate against real code**
   - Owner: Dev (story creator)
   - Rule: ACs must reference actual function/mutation/endpoint names, not assumed names
   - Success criteria: Zero "mutation doesn't exist" or "wrong service name" discoveries during implementation
   - Trigger: All future story creation

### Technical

3. **SSE Streaming test coverage gap**
   - Owner: TBD
   - Priority: Medium
