## Successes

### 1. Shared Tracing Modules Pattern

`tracing.js` (backend) and `tracing.py` (OPEA services) created in 7.1/7.2 and reused across all subsequent stories. Single-point configuration for SDK init, PII redaction, and resource attributes. This pattern dramatically reduced per-story integration effort.

### 2. Safe-Default Gating

Services disabled by default (`ENABLE_OBSERVABILITY=0`), activated only when flag set. Kong plugin created disabled then conditionally enabled (7.9) — eliminates race windows. Zero impact on existing deployments when disabled.

### 3. Fluentd Logging Driver Approach (7.6)

Chose Docker fluentd logging driver over filelog receiver. Avoids root requirements, centralized via YAML anchor (`x-logging: &fluent-logging`), applied to all 33 services. Docker dual logging (20.10+) keeps `docker logs` functional.

### 4. Dual-Mode Deployment Mastery

Single `docker-compose.yaml` supports both `docker compose up` and `docker stack deploy`. Consistent pattern across all infrastructure stories (7.5–7.7): profiles for compose, env vars for Swarm, `mode: global` for Collector.

### 5. Zero Production Incidents

Full observability stack deployed without any production regressions. All 1060+ backend tests, 99+ OPEA tests, 1155 frontend tests pass throughout. Test environment guards (`NODE_ENV=test` → no-ops) preserved existing suites.

### 6. Descope Discipline (7.10)

Story 7-10 identified as "testing-the-testing anti-pattern" early. Observability disabled by default, upstream products mature, health-check one-liner sufficient. Clean descope with documented rationale — saved effort without value loss.

## Challenges

### 1. Import Order Discipline (4 stories: 7.1–7.4)

OTel SDK monkey-patches modules at load time. `tracing.js`/`tracing.py` must be imported FIRST. Violated in 7.2, 7.3, 7.4 reviews — tracing imported after app code. No linter rule catches this. Review caught it every time, but it kept recurring.

### 2. Span Placement Errors (3 stories: 7.2, 7.3, 7.8)

Spans placed around metadata calls instead of actual work, yielding ~0ms durations. Story 7.3 had ingest span wrapping only attribute reads, not ingestion logic. Review caught this, but the pattern repeated across stories.

### 3. Missing Error Context in Spans (4 stories: 7.1, 7.2, 7.3, 7.8)

Recurring pattern: `recordException()` called without `span.setStatus(ERROR)`, or exception handling missing entirely. Same review feedback given in 4 stories. The team didn't internalize the lesson from earlier stories.

### 4. PII Protection Complexity (4 stories: 7.1, 7.2, 7.3, 7.8)

Attribute sanitization inconsistent across services. Each service created its own PII denylist (DRY violation flagged in 7.8). No shared library emerged despite the pattern being obvious after 7.1.

### 5. Runtime Verification Gap (7.5–7.11)

E2E runtime testing consistently deferred across infrastructure stories. Metric names, dashboard queries, alert thresholds verified via unit tests only. Multiple stories noted "needs runtime verification" but no story actually performed it. Dashboards and alerts required post-merge fixes (commits `bcce6262`, `27f73cc1`, `549f393d`).

### 6. OPEA Framework Limitations (7.2, 7.3)

OPEA's `MicroService` wrapper hides the FastAPI app instance. TEI embedding calls lack trace propagation (internal HTTP client). Cannot instrument framework internals without upstream changes.

1. **Review feedback not internalized:** Error context in spans flagged in 4 consecutive stories. Team fixed per-story but didn't codify the pattern. A shared checklist or span creation template would prevent recurrence.

2. **Runtime verification debt compounds:** Deferred runtime testing led to 3 post-merge fixes for dashboards and alerts. The fix-commit cycle (3 commits on 7-11 after merge) shows the cost of deferred verification.

3. **Epic 4 commitments abandoned:** 0/6 action items completed. The retro-to-action pipeline is broken. Future retros must track commitments in sprint-status or a visible artifact.

4. **Descope as a strength:** 7-10 descope was clean, documented, and timely. The team correctly identified a low-value story and redirected effort. This is a model for future descoping decisions.

5. **OTel expertise built:** Team now understands Python vs Node.js SDK differences, dual-mode deployment, span lifecycle, and cardinality management. This knowledge is transferable to future infrastructure work.

6. **Safe-default pattern works:** Every service disabled by default with zero runtime impact. This should be the standard for all optional infrastructure stories going forward.
