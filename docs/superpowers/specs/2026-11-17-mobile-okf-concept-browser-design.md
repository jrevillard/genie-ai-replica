# Mobile OKF concept-tree browser — design (#1939)

Date: 2026-11-17 · Status: DRAFT for builder check · Wave: mobile OKF parity (David, 2026-11-17)

## Intent and why

The web app lets an end user browse an OKF repository's indexed concepts
(the W9 concept-tree browser: progressive tree, per-concept markdown,
history, download). The mobile app has ZERO OKF capability — the generated
Dart client carries no OKF endpoints at all. This wave ships the browser
screen so mobile reaches end-user parity around queries. It is the
foundation item of the mobile parity wave: #1937 (chat citations) and
#1938 (related-sources panel) wire their entries to THIS screen.

**HARD FENCE (David, 2026-11-17): zero Admin Dashboard functionality in
the mobile app.** Every endpoint this feature touches is a citizen-scoped
read. No Studio, no lifecycle, no curation, no admin readouts — ever, in
this wave.

## Goals

1. The three citizen OKF routes exist in the generated Dart client, kept
   honest by the existing api-client drift gate.
2. A browser screen on the app's DS tokens: progressive concept tree,
   detail pane, back/forward, related-concept chips, download,
   empty/unavailable arms.
3. The screen is reachable (temporary drawer entry; real entries land with
   #1937/#1938).

## Non-goals

- No admin surfaces (the fence above).
- No chat-citation rendering, no sidebar changes (their issues own those).
- No backend behavior change: the routes exist and serve under open scope
  mode; this wave only makes them VISIBLE to the generator. The legacy RAG
  pipeline's request/response contract is likewise untouched — the wave
  must not degrade any of its existing capabilities.
- No HTML rendering in concept bodies (see Markdown, below).
- No QR/deep-link provisioning, no certificate pinning (backlog notes).

## Anti-goals (what would make this a failure)

- A second, hand-written HTTP idiom beside the generated client (two
  client idioms = the drift gate stops seeing one of them).
- A concept body rendering raw HTML (XSS on mobile).
- Distinguishing a fenced/unpublished repo from a missing one (404 is 404 —
  the server's anti-enumeration contract must survive the client).

## Constraints

- The generated client is `openapi_client/` (pubspec name `openapi`),
  regenerated by `scripts/generate-api-client.sh`; the spec is extracted by
  `scripts/build-openapi-spec.js` under a pinned env envelope
  (determinism: regenerations are byte-identical). NEVER hand-edit
  `openapi_client/`.
- DS tokens only (`AppTokens`, DsButton/DsCard/DsInput/DsModal/DsSpinner/
  DsStateDisplay); no raw colors or literals.
- i18n: all 14 locale maps in `lib/i18n/locales/*.dart`; keys are strings,
  inserted verbatim.
- Tests + coverage must not decrease; the smoke harness extends per story.
- Flutter 3.41.7 on the dev host; `flutter test` runs locally.

## The decided parts (David's rulings, 2026-11-17)

1. **Spec strategy: annotate okf-server.** The spec builder reads
   gov-chat-backend only — that is why the client has zero OKF endpoints.
   The three citizen routes get swagger-jsdoc annotations in okf-server
   (`GET /api/okf/repos/:repo_id/concept-tree`, `GET
   /api/okf/repos/:repo_id/concepts/:concept_id`, `GET
   /api/okf/concepts/resolve-repo`), and `build-openapi-spec.js` is
   extended to include okf-server's annotated surface. The drift gate then
   pins the whole mobile-facing contract — one spec source of truth, no
   #1588-class drift.
2. **Entry: temporary drawer entry now — a TYPED repo id** (the builder
   check's question). No fixed repo is seeded anywhere in the stack, and
   provisioning one from the client would be an admin write inside a
   citizen-scoped-only wave. The temp entry takes the repo id as input;
   the real entries (citation Browse buttons, sidebar rows) land with
   #1937/#1938 as filed.
3. **Markdown: no-HTML default.** `flutter_markdown` defaults — no HTML
   extension. Concept bodies render as markdown; raw HTML never executes.
   Same safety outcome as the web's DOMPurify pipeline without a sanitizer
   dependency.

## The screen (behavior contract, mirrored from the web's W9 browser)

- **Progressive tree**: first page `GET concept-tree?limit=200&offset=0`;
  "Show more" fetches the next page at offset = loaded count; the button
  disappears when rows < 200 or loaded >= total. A superseded load never
  commits over a newer one (stale-guard by repo).
- **Detail pane**: tapping a row fetches the concept card (`GET
  concepts/:id`); renders `body` as markdown (no-HTML), the `title` in the
  pane header; related-concept chips from the card's `links[]` (deduped,
  label fallback to id) — tapping a chip is a FORWARD navigation.
- **History**: back/forward over visited concepts; a new visit truncates
  the forward tail; re-tapping the current entry is a no-op; boundary
  presses do nothing. Back-to-list clears the selection but keeps history.
- **Arms**: while loading with an empty tree → spinner; nothing selected →
  the select hint; concept unavailable → honest notice; repo 404 → the
  unavailable arm ("cannot be browsed right now"), never an error toast.
  **The full unavailable mapping mirrors the web's `fetchOkfConcept`
  exactly (builder-check resolution, the web precedent): 403, 404 and 501
  all render the unavailable arm** — a 403 is the deployment's closed
  scope posture, which the user cannot fix from the client, so masking it
  as an error would violate the honest-arms ruling just as hard as
  masking a 404. **401 after the AuthInterceptor's refresh path gave up is
  NOT an arm**: the session is dead app-wide, and the screen hands the
  failure to the app's existing re-auth flow (no local retry, no
  unavailable arm, no toast of its own).
- **Download**: writes the selected concept's `body` to a local `.md` file
  (share/save), disabled until a concept is selected.
- **Notice**: "Showing what is indexed now" — the citation clause appears
  only when opened from a citation (not this wave; the field arrives with
  #1937's wiring).
- **Anti-enumeration**: a 404 on the tree or the concept renders the
  honest unavailable arm; no retry-on-404, no fenced/absent distinction.

## What is left to the builder

- The Dart screen's widget composition and state container (follow the
  app's riverpod conventions; the service_tree_panel's guarded-fetch idiom
  is the house pattern for locale refetch + supersession).
- Exact i18n key names (okfBrowser.* namespace, mirroring the web's keys
  where the wording matches).
- The smoke harness leg's shape (the OKF smoke phase gains a mobile leg or
  the browser screen gets its own fixture run — builder's call within the
  standing smoke rules). **Provisioning precedent (builder-check
  resolution): the existing OKF smoke harness ALREADY provisions, serves
  and cleans up its own repos with the admin token as a DEV-SYSTEM harness
  (run-smoke-ceiling.js creates → publishes → ingests → purges). The
  mobile smoke leg follows the same pattern: the HARNESS provisions a
  serving repo with the admin token; the APP consumes it citizen-scoped.
  The fence governs the app's features, not the dev harness.**
- Annotation phrasing for the three routes (swagger-jsdoc style must match
  the backend's existing annotations).

## Builder-check resolutions (my calls — check while reading)

1. **The concept-GET schema is the CITIZEN CARD projection** — `{repo_id,
   concept_id, graph_name, bundle_version, title, labels, summary, body,
   links, sources}` — not the role-dependent union. The drift gate pins
   one schema and the fence makes the citizen card the mobile's contract;
   documenting the union would put steward-only fields (`max_doc_chars`,
   the full meta row) into a citizen-only Dart model. The endpoint's
   description text notes the steward variant exists server-side; the
   schema is what the mobile consumes.
2. **The unavailable mapping is 403/404/501 → unavailable arm; 401 → the
   app's re-auth flow** (folded into the Arms contract above — the web's
   own mapping is the precedent).
3. **The temp drawer entry takes a TYPED repo id** (no fixed repo exists
   to pre-seed; see the decided parts).
4. **The smoke leg provisions via the dev-harness admin-token precedent**
   (folded into the builder notes above).

## Windows regeneration recipe (operational)

`generate-api-client.sh` is POSIX-only (env -i strips what node.exe
needs). The established local recipe: a pinned openapi-generator JAR shim
outside the tracked scripts (the npm CLI install is AV-blocked on this
host), running the same pinned version from `openapitools.json` over the
same extracted spec, followed by the array-file patch the script applies.
The committed client must remain byte-identical to what CI's drift gate
would produce — run the `--check` equivalent before pushing any backend
contract change. If the shim is missing, regenerating on WSL is the
fallback (the script's own environment contract holds there).

## Retrieval modes — legacy, OKF Only, Hybrid (David, 2026-11-17)

The backend retrieval posture serves THREE configured modes — `legacy`,
`okf_only`, `hybrid` (the retrieval-config contract the admin surface
already reads). **The mobile app must support all of them, and the LEGACY
RAG QUERY PIPELINE MUST REMAIN FULLY FUNCTIONAL WITH ITS EXISTING
CAPABILITIES.** Concretely:

- **Mode-aware source rendering.** A chat answer's `source_documents` may
  be legacy documents, OKF concepts, or BOTH in one list (hybrid). Every
  source row is classified by the shared predicate
  (`source === 'okf-concept' || conceptId present`) — never by absence of
  an OKF marker:
  - a LEGACY document renders exactly as it does today (title, file
    name, format, the doc-repo view route) with NO OKF badge and NO
    Browse-repository affordance;
  - an OKF concept carries the badge and the Browse affordance;
  - a hybrid answer renders both kinds side by side in one list, each
    through its own route.
- **The legacy wire contract is untouched.** This wave adds nothing to
  the query request or response shapes; the SSE `extra` passthrough and
  the non-streaming fallback keep their existing behavior byte-for-byte.
  The OKF citation fields ride the metadata the backend already sends
  when an OKF-sourced chunk is retrieved.
- **Regression pins are part of the definition of done.** Unit tests
  pin, per mode: a legacy-only answer renders no OKF affordances; an
  OKF-only answer renders the badge + Browse; a hybrid answer renders
  both kinds correctly in one list; and the legacy document open path
  (the doc-repo view route) keeps working — including the dead-auth fix
  that ships with #1938, which is a LEGACY capability restored, not an
  OKF feature.
- **The browser screen is mode-independent.** Browsing is per-repo and
  reached only from OKF citations; a legacy-only deployment simply never
  shows an OKF affordance, and the screen itself is dormant until reached.
