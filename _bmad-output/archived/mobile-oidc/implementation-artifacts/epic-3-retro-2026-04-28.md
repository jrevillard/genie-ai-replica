## What Went Well

### 1. Two-Layer Network Architecture (Story 3.2)

The pre-flight check (synchronous, < 1ms) + try-catch safety net pattern elegantly accepts TOCTOU as inevitable and provides a fallback. This is a design pattern worth reusing for any network-dependent operation.

### 2. Previous Story Intelligence Chain

Each story inherited lessons from the previous one. Dev Notes documented gotchas (flutter_appauth quirks, test patterns, architectural decisions), preventing repeated mistakes. The chain 3.1 → 3.2 → 3.3 was smooth.

### 3. Fake-Based Testing (No Mockito)

`FakeConnectivityChecker`, `FakeTokenStorage`, `_RecordingAuthLogger` — consistent, simple, maintainable. No framework-level mock fragility. Tests are deterministic and readable.

### 4. Auto-Recovery Design (Story 3.3)

Single auto-retry with manual fallback. Avoids infinite retry loops (battery drain) while providing a "the app tries itself" UX. The 500ms debounce (manual Timer, no rxdart dependency) is the right tradeoff.

### 5. Structured Dev Notes

The Architecture / Critical / Testing / References format enabled the dev agent to work autonomously. Reviews focused on real issues, not onboarding questions.

## Challenges

### 1. Race Conditions Between Async Methods (All 3 Stories)

`validateTokens()` vs lifecycle (3.1), `retryAuthorize()` vs `authorize()` (3.2), `refreshToken()` concurrent calls (3.3). Each was patched with boolean flags + try-finally. **Pattern is pragmatic but not scalable** — adding a new async method requires manually adding guards.

**Deferred items:** 3+ race conditions remain (validateTokens vs logout, authorize vs logout, authorize vs validateTokens).

### 2. Error Classification: Network vs Auth (Stories 3.2, 3.3)

"Is this a network error or an auth error?" recurred across stories. `_isNetworkError()` heuristic (keyword matching on exception codes) is inherently fragile. In 3.3, a critical bug was found: generic catch in `authorize()` marked everything `retryable: true`, including `invalid_grant`.

**Lesson:** `retryable` should default to `false` (pessimistic default = safer).

### 3. `ref.mounted` Guard Omitted (Stories 3.1, 3.3)

Forgot in lifecycle callback (3.1) and in async subscriptions (3.3). Despite being an Epic 1 team agreement, it keeps being missed.

### 4. Growing Test Volume

136 tests for auth alone. While coverage is excellent, the growing volume increases maintenance burden. Story 3.3 alone added 22 tests.

## Key Takeaways

1. Two-layer architecture (pre-flight + safety net) is the right pattern for network resilience
2. `retryable` should always default to `false` — optimistic defaults on error handling are dangerous
3. Boolean flag guards for race conditions work but don't scale — plan for a proper solution in Epic 6
4. Fake-based testing continues to pay off — zero regressions, zero mockito, high maintainability
5. Structured Dev Notes with Previous Story Intelligence are the single biggest quality lever
